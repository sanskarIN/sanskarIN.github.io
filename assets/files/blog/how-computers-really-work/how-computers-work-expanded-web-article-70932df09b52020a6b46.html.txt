<h2 id="chapter-01">01. What makes a computer a computer?</h2>
<p>A computer is a programmable physical system that represents
information, transforms it according to rules, preserves state and
communicates results. A calculator and a data-center server share these
principles, even though their capabilities, scale and interfaces differ
enormously. The important distinction is not size or speed, but the
ability to execute a sequence of operations under program control.</p>
<p>The stored-program model lets a processor obtain instructions and
operands from memory. Historically, early machines often had to be
rewired or configured for a new task; stored programs made
general-purpose reprogramming much easier. Modern implementations may
have separate instruction and data caches while presenting a shared
address space to software. The architecture is therefore not a literal
picture of every physical wire.</p>
<p>The machine can be understood as a hierarchy of abstractions. At the
bottom, voltage and current change in circuits. Logic gates create
Boolean functions. Sequential circuits retain state. A processor
interprets instructions, an operating system manages resources, and
applications use those resources to solve human problems. Each interface
hides details of the layer below it, but performance and correctness
still depend on those details.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Physical signals → Logic &amp;
state → CPU + memory → OS + programs" class="flow"><li>Physical signals</li><li>Logic &amp;
state</li><li>CPU + memory</li><li>OS + programs</li></ol></figure>
<p><strong>A simple calculation:</strong> Entering 7 + 5 triggers input
events, software parses the expression, a processor or runtime computes
12, and a display renders the characters. Many more operations occur
around the addition than in the addition itself.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 2" href="#ref-2">2</a></p>
<h3 id="a-machine-a-model-and-a-program">01.2 A machine, a model and a
program</h3>
<p>Computability is about what a procedure can accomplish in principle,
not how quickly a particular computer runs it. A finite program can
repeatedly read inputs, change state and choose its next operation. A
model such as a Turing machine idealizes memory as unbounded; a physical
laptop has finite storage, power and time. General-purpose hardware
approximates the model within those limits.</p>
<p>An algorithm specifies a method independently of its implementation.
A program expresses that method in a language, while a running
computation consists of actual state changes. The same sorting algorithm
can be implemented on a microcontroller, a multicore CPU or a GPU, but
its cost depends on data movement and execution architecture.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Problem → Algorithm → Program →
Execution" class="flow"><li>Problem</li><li>Algorithm</li><li>Program</li><li>Execution</li></ol></figure>
<p><strong>Trace a tiny algorithm:</strong> Start with sum = 0. Read 4,
7 and 2; update sum to 4, 11 and 13. The program is the rule; the
successive sums are the changing machine state. A larger memory does not
change the rule, but permits larger input.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 2" href="#ref-2">2</a></p>
<h3 id="hardware-and-software-contracts">01.3 Hardware and software
contracts</h3>
<p>Abstraction is a contract rather than a claim that lower layers do
not exist. A processor promises instruction behavior, a system-call
interface promises operations on OS-managed resources, and a library
promises a programming interface. A compiler can change the emitted
machine code while preserving the language’s required behavior.</p>
<p>Different contracts have different compatibility consequences. A
source program may be portable if it avoids platform-specific
assumptions. A compiled executable depends on an instruction set,
operating-system ABI and required libraries. Even a compatible binary
can be slower on another machine because the physical resources
differ.</p>

<h3 id="computer-families-and-system-boundaries">01.4 Computer families
and system boundaries</h3>
<p>A microcontroller typically combines processing, memory and
peripheral controllers in one chip and often performs a dedicated
control task. A desktop prioritizes interactive applications and
flexible peripherals. Servers prioritize capacity, reliability and
concurrent workloads. Supercomputers coordinate many processors and
accelerators through high-speed networks.</p>
<p>A system-on-chip integrates multiple subsystems, often including CPU
cores, graphics, memory controllers and media engines. Integration
reduces some communication overhead, while a modular system can offer
replaceable components. Neither approach makes all workloads faster; the
required interfaces and resource limits determine suitability.</p>

<h2 id="chapter-02">02. A brief history of programmable machines</h2>
<p>Mechanical calculation preceded electronic computing by centuries.
Nineteenth-century designs such as Babbage’s Analytical Engine
anticipated programmable operations, although the complete machine was
not constructed in his lifetime. Electromechanical relay machines and
electronic vacuum-tube machines later demonstrated large-scale
computation. Early electronic computers were expensive, bulky and often
specialized.</p>
<p>The Manchester Baby executed a stored program in 1948; EDSAC became
an early practical stored-program service in 1949. Transistors displaced
many vacuum tubes because smaller solid-state devices offered advantages
in size, energy use and reliability. Integrated circuits placed many
components on a single chip, and the microprocessor integrated the
processing function into a chip in the early 1970s. Affordable personal
computers, graphical interfaces, networking and mobile systems
subsequently broadened access to computing.</p>
<p>Today’s computing landscape spans microcontrollers, personal
computers, servers, supercomputers and specialized accelerators.
Progress has depended on manufacturing, architecture, software tools and
communications together. The history is not a sequence of one inventor
replacing another; it is a long interaction among mathematical ideas,
engineering and practical needs.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Mechanical → Electronic →
Integrated circuits → Networked systems" class="flow"><li>Mechanical</li><li>Electronic</li><li>Integrated circuits</li><li>Networked systems</li></ol></figure>
<p><strong>Why the stored program matters:</strong> Changing an
algorithm can mean loading new bytes into memory rather than rebuilding
circuitry. Hardware remains general-purpose within the capabilities
defined by its instruction set.</p>
<p class="sources">Sources: <a aria-label="Reference 2" href="#ref-2">2</a>, <a aria-label="Reference 3" href="#ref-3">3</a></p>
<h3 id="from-mechanical-calculators-to-relays">02.2 From mechanical
calculators to relays</h3>
<p>Mechanical devices encoded numbers through physical positions of
wheels, gears or other components. Addition required moving components
in a controlled sequence; carry mechanisms transferred overflow to the
next digit. Such machines demonstrate that arithmetic need not be
implemented with electricity.</p>
<p>Electromechanical relays make switching decisions using electrically
controlled mechanical contacts. Networks of switches can implement
conditional logic, but the movement introduces delay and wear.
Electronic switching removed much of this mechanical bottleneck. The
underlying ideas of representation, arithmetic and control continued
across these technological changes.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Mechanical state → Relay logic →
Electronic logic → Integrated logic" class="flow"><li>Mechanical state</li><li>Relay logic</li><li>Electronic logic</li><li>Integrated logic</li></ol></figure>
<p><strong>A carry is a physical event:</strong> When a decimal wheel
advances from 9 to 0, the next wheel must increase. In a binary
electronic adder, a carry plays a similar mathematical role, although
its implementation is a voltage signal rather than a mechanical
linkage.</p>
<p class="sources">Sources: <a aria-label="Reference 2" href="#ref-2">2</a>, <a aria-label="Reference 3" href="#ref-3">3</a></p>
<h3 id="stored-programs-and-early-architecture">02.3 Stored programs and
early architecture</h3>
<p>Early programmable systems used various ways to specify a sequence of
operations, including external media and physical configuration. With
stored programs, instructions can reside in addressable memory. This
lets software select different routines, branch according to computed
values and load new programs with comparatively little physical
alteration.</p>
<p>The conceptual architecture often described as von Neumann organizes
a processor, memory and input/output around a stored program. Real
systems diverge from the simple block diagram: instruction and data
paths can be separate, memory is hierarchical, and devices can transfer
data independently. The model remains useful as a way to reason about
program state.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Instruction memory → Control unit →
ALU + registers → Data memory" class="flow"><li>Instruction memory</li><li>Control unit</li><li>ALU + registers</li><li>Data memory</li></ol></figure>
<p><strong>Program changes without rebuilding:</strong> Imagine memory
containing a sequence that adds two numbers. Replacing that sequence
with one that compares them changes the work performed by the same
processor. No new arithmetic wiring is required if the ISA supports both
operations.</p>
<p class="sources">Sources: <a aria-label="Reference 2" href="#ref-2">2</a>, <a aria-label="Reference 3" href="#ref-3">3</a></p>
<h3 id="microprocessors-personal-computers-and-cloud">02.4
Microprocessors, personal computers and cloud</h3>
<p>Integrated circuits made it practical to connect many electronic
components without individually wiring every transistor. A
microprocessor places instruction-processing circuitry on a chip;
supporting memory and I/O can be on other chips or integrated nearby.
Increased integration lowered barriers to building small, affordable
computing systems.</p>
<p>Personal computers made interactive applications widely accessible,
while networks let machines cooperate. Cloud computing uses pooled
infrastructure, virtualization and automated management to provide
computing resources as services. A cloud server is still a physical
computer: a request consumes processor time, memory bandwidth, storage
and network capacity somewhere in a data center.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Chip integration → Personal systems
→ Networks → Pooled services" class="flow"><li>Chip integration</li><li>Personal systems</li><li>Networks</li><li>Pooled services</li></ol></figure>
<p><strong>Local versus remote execution:</strong> Editing a file
locally can use your own CPU and SSD. Editing through a web service may
also send changes to a remote machine for persistence. In both cases,
electrical switching and instruction execution remain fundamental.</p>
<p class="sources">Sources: <a aria-label="Reference 2" href="#ref-2">2</a>, <a aria-label="Reference 5" href="#ref-5">5</a>, <a aria-label="Reference 10" href="#ref-10">10</a></p>
<h2 id="chapter-03">03. Electricity, silicon and transistors</h2>
<p>Voltage is electrical potential difference; current is the rate of
charge flow. A digital circuit uses ranges of voltage to encode logical
values. The exact levels depend on the technology, supply voltage and
design. A logical zero is not always exactly zero volts, and a logical
one is not universally five volts. Noise margins allow imperfect
physical signals to be treated reliably as discrete symbols.</p>
<p>Silicon is a semiconductor. Introducing selected impurity atoms
changes its charge-carrier population: donor doping produces n-type
material and acceptor doping produces p-type material. In a MOS
field-effect transistor, an insulated gate controls the conductivity of
a channel between source and drain. An n-channel device normally
conducts strongly when its gate is sufficiently positive relative to its
source; a p-channel device responds to the opposite polarity. Real
devices have leakage, capacitance and finite switching times.</p>
<p>Complementary MOS (CMOS) combines n-channel and p-channel networks.
In a simple inverter, the p-channel device connects the output toward
the supply when the input is low, while the n-channel device connects it
toward ground when the input is high. Ideally there is no direct static
conduction path between rails in either stable state, although real
circuits consume leakage power and switching energy.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Input voltage → MOS gate → Channel
control → Output voltage" class="flow"><li>Input voltage</li><li>MOS gate</li><li>Channel
control</li><li>Output voltage</li></ol></figure>
<p><strong>Dynamic power:</strong> A common approximation is P = alpha C
V^2 f, with switching activity alpha, effective capacitance C, supply V
and clock frequency f. Voltage reduction can save energy, but may reduce
switching speed and operating margin.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 4" href="#ref-4">4</a>, <a aria-label="Reference 5" href="#ref-5">5</a>, <a aria-label="Reference 32" href="#ref-32">32</a></p>
<h3 id="voltage-charge-and-digital-noise-margins">03.2 Voltage, charge
and digital noise margins</h3>
<p>Electric charge is a physical property, voltage describes potential
difference, and current measures charge flow per unit time. Capacitors
store charge; resistive paths dissipate energy. On-chip wires have
electrical properties that affect both speed and power. Digital circuits
still obey analog physical laws.</p>
<p>To communicate a logical value reliably, a transmitting circuit must
produce a voltage range that a receiving circuit recognizes. Designers
specify acceptable input and output levels. The separation between these
ranges provides tolerance to noise. Signals near a threshold can be
ambiguous; digital abstractions are valid only when electrical and
timing requirements are met.</p>

<h3 id="semiconductor-junctions-and-mosfet-control">03.3 Semiconductor
junctions and MOSFET control</h3>
<p>Pure silicon has a crystal structure whose electrical behavior can be
modified by adding carefully controlled impurities. Donor and acceptor
doping change the availability of mobile charge carriers. Junctions
between differently doped regions exhibit directional electrical
behavior, which is central to many semiconductor devices.</p>
<p>A metal-oxide-semiconductor field-effect transistor uses an electric
field from its gate to influence conduction between source and drain.
The gate is insulated from the channel in the idealized structure. An
n-channel device generally conducts strongly with a sufficiently
positive gate-to-source voltage; p-channel behavior has opposite
polarity. Actual devices have leakage, parasitic capacitances and
continuous current-voltage characteristics.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Gate voltage → Electric field →
Channel conductance → Current path" class="flow"><li>Gate voltage</li><li>Electric field</li><li>Channel conductance</li><li>Current path</li></ol></figure>
<p><strong>Switch abstraction and its limits:</strong> An ideal switch
has zero resistance when closed and infinite resistance when open. A
real MOSFET has finite on-resistance and off-state leakage. The
simplified model helps explain logic, but detailed circuit simulation is
needed for power and timing design.</p>

<h3 id="cmos-networks-and-switching-energy">03.4 CMOS networks and
switching energy</h3>
<p>Complementary MOS logic uses pull-up and pull-down networks to drive
an output toward its supply rails. In a simple inverter, the pMOS
pull-up conducts for a low input and the nMOS pull-down conducts for a
high input. NAND and NOR gates use different series and parallel
transistor arrangements to implement their truth tables.</p>
<p>Charging and discharging capacitance consumes energy. A common
first-order model for dynamic power is P = alpha C V^2 f, where alpha
represents switching activity under the chosen convention, C is
effective capacitance, V is supply voltage and f is clock frequency.
Static leakage and short-circuit current also contribute, so the formula
is not a complete chip-power model.</p>

<h2 id="chapter-04">04. How a microchip is manufactured</h2>
<p>Chip development begins with architecture, circuit design and
verification. Engineers describe digital behavior using hardware
description languages, synthesize logic and perform placement and
routing. Timing analysis checks whether signals can reach their
destinations within design constraints. Physical verification checks
layout rules and connectivity before the design is sent for
fabrication.</p>
<p>Manufacturing starts with highly purified silicon wafers. Repeated
processes deposit films, coat surfaces with photoresist, expose patterns
using lithography, develop the resist, etch selected regions and modify
material properties through processes such as implantation. The sequence
varies with the device and layer. Metal interconnect layers then connect
the transistors into functional circuits. Precision alignment of many
patterned layers is essential.</p>
<p>Finished wafers undergo electrical testing and are separated into
dies. Packaging provides electrical connections, physical protection and
paths for heat removal. Some packages contain multiple dies or chiplets
connected by advanced interconnects. Devices are tested again and may be
classified according to measured characteristics. Yield, manufacturing
cost and power consumption influence commercial design decisions. A
process-node name is a technology-generation label, not a simple
measurement of every transistor feature.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Design &amp; verify → Pattern wafer
→ Build interconnect → Test &amp; package" class="flow"><li>Design &amp; verify</li><li>Pattern wafer</li><li>Build interconnect</li><li>Test &amp; package</li></ol></figure>
<p><strong>Design versus fabrication:</strong> A chip architecture
specifies what a design should do. A fabrication process determines how
its devices and wiring are physically realized. Identical architectural
instructions can be implemented by chips made with different
technologies.</p>
<p class="sources">Sources: <a aria-label="Reference 5" href="#ref-5">5</a>, <a aria-label="Reference 6" href="#ref-6">6</a></p>
<h3 id="from-hardware-specification-to-mask-layout">04.2 From hardware
specification to mask layout</h3>
<p>Chip development starts with a specification: instruction behavior,
interfaces, power budget, performance targets and reliability
constraints. Hardware description languages describe the behavior and
structure of circuits. Engineers verify modules with simulation,
assertions and other techniques before manufacturing.</p>
<p>Logic synthesis maps register-transfer descriptions onto cells
supported by the manufacturing process. Physical design then places
those cells, routes wires and constructs power and clock networks.
Timing, voltage drop, signal integrity and design rules are checked
repeatedly. A design that simulates logically may still be physically
impractical if routing or timing constraints cannot be satisfied.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="RTL description → Synthesis → Place

<p><strong>A timing constraint:</strong> A circuit targeting 1 GHz has a
nominal 1 ns clock period. Register delays, combinational paths, clock
uncertainty and setup requirements must fit into that budget. Adding
more logic between registers may force a redesign or lower clock

<h3 id="wafer-processing-and-lithography">04.3 Wafer processing and
lithography</h3>
<p>Manufacturing builds patterned material layers on a semiconductor
wafer. Deposition adds thin films; lithography creates patterns in
photoresist using controlled light; etching removes selected material;
implantation or related techniques modify material properties. Repeated
processing forms active devices and multiple levels of interconnect.</p>
<p>The dimensions involved depend on the process and on the particular
feature being manufactured. Process-node names are not a simple
measurement of every transistor dimension. Alignment between layers,
defect density and process variation matter as much as nominal feature
size. Measurement and process control help manufacturers detect
departures from the intended geometry.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Deposit film → Expose pattern →

<p><strong>Why alignment matters:</strong> A contact must overlap the
appropriate underlying structure. If patterns shift too far relative to
one another, a connection can become resistive, short to another feature
or fail entirely. Overlay control is therefore essential to reliable
chips.</p>

<h3 id="packaging-testing-and-yield">04.4 Packaging, testing and
yield</h3>
<p>After fabrication, dies are tested and separated from the wafer.
Packaging provides electrical connections, mechanical support and a path
for heat removal. Modern packages may integrate multiple dies, stacked
memory or interposers. The final product includes the package and its
connections, not simply a piece of patterned silicon.</p>
<p>Manufacturing defects, variation and testing limits affect yield, the
proportion of usable products. Some dies can be classified into
different performance or power grades, depending on their measured
properties. Tests may include functional patterns, memory checks and
stress tests, but no finite test guarantees that every possible defect
is absent.</p>

has 500 candidate dies and 430 pass its test criteria. Yield is 430/500
= 86%. This simple ratio does not include packaging losses, different

<h2 id="chapter-05">05. Binary, hexadecimal and signed integers</h2>
<p>A bit represents one of two logical states. Eight bits form a byte;
an unsigned n-bit field has 2^n possible patterns and represents
integers from 0 through 2^n - 1 under ordinary binary encoding. The
place values in binary are powers of two. Hexadecimal uses sixteen
symbols and provides a compact notation because one hexadecimal digit
corresponds to four bits.</p>
<p>Two’s complement encodes signed integers by assigning the most
significant bit a negative weight. An eight-bit signed value ranges from
-128 through 127. The pattern 11111111 is 255 when unsigned and -1 when
interpreted as signed. Hardware often uses the same binary addition
circuit for both signed and unsigned values; the meaning of overflow
differs. Unsigned addition wraps modulo 2^n in fixed-width arithmetic,
while signed overflow rules depend on the instruction or programming
language.</p>
<p>Byte order describes how a multi-byte number is arranged at
consecutive memory addresses. Little-endian stores the least significant
byte first; big-endian stores the most significant byte first. It does
not reverse the bits within every byte. A data type supplies
interpretation, constraints and operations; the same bits can encode
many different kinds of information.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Decimal 13 → Binary 1101 → Hex 0D →
Byte 00001101" class="flow"><li>Decimal 13</li><li>Binary 1101</li><li>Hex 0D</li><li>Byte 00001101</li></ol></figure>
<p><strong>Worked conversion:</strong> 13 = 8 + 4 + 1. In eight-bit
two’s complement, -13 is 11110011: invert 00001101 and add one. A 32-bit
value 0x12345678 has bytes 78 56 34 12 in little-endian order.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 7" href="#ref-7">7</a></p>
<h3 id="positional-notation-and-bit-manipulation">05.2 Positional
notation and bit manipulation</h3>
<p>A base-b number assigns each digit a weight that is a power of b.
Binary has only two digit values, but the same positional principle as
decimal. Hexadecimal is especially convenient for debugging because
groups of four binary bits map exactly to hexadecimal digits.</p>
<p>Bitwise operators act on corresponding bits independently. AND can
isolate selected fields, OR can set bits, and XOR can toggle them.
Shifts move bit positions; right shifts can be logical or arithmetic
depending on the operation and language. Fixed-width shifts must respect
the rules for shift counts and discarded bits.</p>

<h3 id="signed-arithmetic-and-overflow">05.3 Signed arithmetic and

<p>A fixed-width integer has a finite set of bit patterns. In unsigned
interpretation, all patterns represent nonnegative values. In two’s
complement interpretation, the highest bit contributes a negative place
value. The arithmetic circuit can often use the same addition mechanism
for both interpretations.</p>
<p>Overflow is a question about whether the mathematical result fits in
the chosen interpretation. An unsigned carry out indicates an
out-of-range unsigned sum. For signed addition, overflow occurs when two
operands with the same sign produce a result with the opposite sign.
Programming languages differ in how they handle these cases; checking a
result requires knowing both the representation and the language
contract.</p>

<h2 id="chapter-06">06. Text, images, audio and floating point</h2>
<p>Text is represented by character encodings. Unicode assigns code
points to characters and other textual elements; UTF-8 maps these code
points to sequences of one to four bytes. ASCII letters occupy one byte
in UTF-8, but many other scripts require multiple bytes. A displayed
character may involve several code points, so counting bytes, code
points and user-perceived characters gives different results.</p>
<p>A raster image is an array of samples such as RGB values. An
uncompressed 1920 by 1080 image at 24 bits per pixel occupies 6,220,800
bytes before metadata or row padding. Audio stores sampled signals:
sampling rate specifies samples per second, while bit depth describes
quantization precision. Lossless compression preserves the original
information; lossy compression discards selected detail to reduce size.
Encoded video often exploits similarity across frames as well as spatial
redundancy.</p>
<p>Floating-point values represent a finite set of numbers using sign,
exponent and significand fields. IEEE 754 binary32 has one sign bit,
eight exponent bits and twenty-three stored fraction bits. Its ordinary
normalized values have an implicit leading one. Some decimal fractions
have no finite binary expansion, so calculations may round. Special
patterns encode infinities, NaNs, zeros and subnormal values. Use
integer units or an appropriate decimal type for exact decimal
accounting where required.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Human meaning → Encoding → Bytes in

<p><strong>Why 0.1 is tricky:</strong> The decimal fraction 1/10 repeats
in binary, much as 1/3 repeats in decimal. A finite binary
floating-point format approximates it, so arithmetic comparisons require
attention to rounding.</p>

representation. UTF-8 uses variable-length byte sequences; ASCII code
points have the same single-byte encoding as ASCII. Continuation-byte
patterns distinguish later bytes of a multi-byte sequence. Decoders must
reject or otherwise handle invalid sequences according to their API
contract.</p>

sequences of code points can form one user-perceived character. Case
conversion, normalization and line breaking require rules beyond
indexing a byte array. A user interface that truncates text after an
arbitrary byte count may cut a UTF-8 sequence or split a visible
character.</p>

<h3 id="sampling-pixels-and-compression">06.3 Sampling, pixels and
compression</h3>
<p>Digital media represents signals with finite samples. Image
resolution determines how many sample positions are available, while
color format determines the components and precision at each position.
Audio sampling converts changes over time into a discrete sequence;
reconstruction of a suitably band-limited signal requires sufficient
sampling frequency and filtering.</p>
<p>Compression reduces representation size. Lossless methods exploit
redundancy without changing the reconstructed data; lossy methods permit
controlled approximation. Image and video encoders can transform blocks,
predict from neighboring data and encode residual differences. Decoding
must follow the format’s rules, and quality depends on the signal and
encoding decisions.</p>

values can remove their shared leading digits, leaving a result with
relatively poor accuracy. Reordering operations can change results
because finite-precision addition is not generally associative. A
mathematically equivalent expression may have a different numerical
error profile.</p>

<h2 id="chapter-07">07. Logic gates and Boolean algebra</h2>
<p>A gate realizes a Boolean function. NOT reverses its input; AND is
true when both inputs are true; OR is true when at least one input is
true; XOR is true when the inputs differ. NAND and NOR negate AND and OR
respectively. Either NAND alone or NOR alone can express all Boolean
functions through combinations of gates.</p>
<p>Digital designers combine gates into combinational circuits, whose
outputs are determined by current inputs after propagation delay. A
multiplexer selects one of multiple inputs using control bits. A decoder
selects an output based on a binary code. Comparators test ordering or
equality. Such circuits can be expressed using truth tables, Boolean
expressions or structural connections. Logic synthesis translates
descriptions into technology-specific networks and optimizes area, delay
and power.</p>
<p>Computation is not instantaneous. Each gate has delay, and wiring
introduces additional capacitance and resistance. The longest relevant
path through combinational logic constrains the minimum clock period in
a synchronous design. A gate-level implementation can be logically
correct yet fail at a target operating frequency if timing constraints
are violated.</p>

<h3 id="boolean-identities-and-universal-gates">07.2 Boolean identities
and universal gates</h3>
<p>Boolean algebra describes functions whose arguments and results
belong to a two-element domain. The identities A AND 1 = A and A OR 0 =
A express neutral elements. De Morgan’s identities connect complement,
conjunction and disjunction, allowing equivalent logic circuits to be
expressed using different gates.</p>
<p>Any Boolean function of finitely many inputs can be expressed as a
disjunction of minterms, one for each input pattern that produces true.
This canonical form is not necessarily efficient. Designers simplify
expressions or use synthesis tools to find implementations with lower
delay, area or power. NAND gates alone suffice because they can
construct NOT, AND and OR.</p>

<h3 id="multiplexers-decoders-and-encoders">07.3 Multiplexers, decoders
and encoders</h3>
<p>A multiplexer connects one selected input to an output. For two
inputs A and B with select S, output Y = (NOT S AND A) OR (S AND B).
Wider multiplexers can choose among more sources and are commonly used
when an arithmetic unit must select operands or a register must choose
its next value.</p>
<p>A decoder converts an encoded value into selected outputs, for
example a two-bit address into four one-hot selection lines. An encoder
performs a related reverse operation; priority encoders define behavior
when more than one input is active. Combinational circuits can exhibit
transient changes during propagation, so timing must be considered
before outputs are sampled.</p>

<h3 id="combinational-logic-and-critical-paths">07.4 Combinational logic
and critical paths</h3>
<p>Combinational circuit outputs depend on current inputs, once signals
have had enough time to propagate. A path is a chain of gates and wires
from an input or register to an output or register. Propagation delay
varies with loading, process, voltage, temperature and the transition
being measured.</p>
<p>A critical path is one that limits the timing target under the
analysis assumptions. Parallel hardware can shorten a sequential
dependency chain, at the possible cost of additional area and power.
Gate count alone is therefore a poor predictor of speed. Designers also
check short paths, because data that changes too early can violate a
receiving register’s hold requirement.</p>

<h2 id="chapter-08">08. Arithmetic circuits, clocks and state</h2>
<p>A full adder receives two operand bits and a carry-in bit. It
produces S = A XOR B XOR Cin and Cout = (A AND B) OR (Cin AND (A XOR
B)). Chaining full adders creates a multi-bit ripple-carry adder; faster
alternatives use parallel carry computation at the cost of extra
hardware. Subtraction can reuse addition by complementing the second
operand and adding one.</p>
<p>Combinational logic alone cannot remember previous inputs. Sequential
circuits add storage, for example latches and edge-triggered flip-flops.
A register groups several storage elements to hold a multi-bit word. A
finite-state machine uses stored state plus current inputs to compute
its next state and outputs. Control units, communication protocols and
device controllers all rely on this idea.</p>
<p>In a synchronous circuit a clock coordinates when state is sampled.
Data must be stable for specified setup and hold intervals around the
sampling edge. Signals crossing unrelated clock domains require
deliberate synchronization; otherwise metastability can cause
unpredictable behavior. Designers must also account for clock skew and
distribution delay. Many modern systems contain several independently
clocked regions rather than a single universal clock.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Operands + carry → Full adder → Sum
+ carry → Register" class="flow"><li>Operands + carry</li><li>Full adder</li><li>Sum
+ carry</li><li>Register</li></ol></figure>
<p><strong>A four-bit addition:</strong> 0101 (5) + 0011 (3) = 1000 (8).
Carries propagate from lower to higher positions. In an unsigned
four-bit field this is valid; in signed four-bit two’s complement it
overflows the range -8 to 7.</p>

<h3 id="full-adders-subtractors-and-carry-networks">08.2 Full adders,
subtractors and carry networks</h3>
<p>A full adder combines three one-bit inputs into a sum bit and carry
bit. The carry records whether at least two inputs are one. Repeating
this structure across bit positions implements addition with a ripple
carry. The dependency on lower bits can make the longest carry path
expensive as width grows.</p>
<p>Carry-lookahead and parallel-prefix techniques compute groups of
propagate and generate conditions so carry information can travel
through a shallower logical network. Subtraction can be represented as A
+ NOT B + 1 for fixed-width two’s complement arithmetic. Arithmetic
hardware may additionally compute flags or comparison conditions,
depending on the ISA.</p>

<h3 id="latches-flip-flops-and-register-files">08.3 Latches, flip-flops
and register files</h3>
<p>A latch can follow its input while an enable condition holds, then
preserve a value when the enable changes. An edge-triggered flip-flop
samples its input around a clock edge and preserves the result between
sampling events. Both require electrical timing conditions for reliable
operation.</p>
<p>A register groups storage elements to hold a word. A register file
adds selection and access ports, allowing an instruction to identify
operand registers and destinations. Additional simultaneous reads or
writes can make the storage circuitry more expensive. Reset and enable
signals control initialization and selective updates where the design
requires them.</p>

<h3 id="finite-state-machines-and-hardware-control">08.4 Finite-state
machines and hardware control</h3>
<p>A finite-state machine maintains one of a finite set of states. A
transition function combines current state and input to choose the next
state. Output logic can depend on state alone or on state and input.
State encoding determines how those abstract states are represented by
storage bits.</p>
<p>Controllers use these machines to sequence operations. A memory
controller, for example, can track whether it is idle, waiting for a
response or completing a request. Real systems may have many interacting
state machines. Verification checks reachable states, legal transitions
and behavior when requests arrive in unexpected orders.</p>

<h2 id="chapter-09">09. CPU anatomy and the instruction set</h2>
<p>An instruction set architecture (ISA) defines the contract visible to
machine-code programs: instruction encodings, registers, supported
operations, address behavior and related rules. Examples include x86-64,
AArch64 and RISC-V. Microarchitecture describes how a particular
implementation realizes that contract. Two processors with the same ISA
can have very different pipelines, caches, power budgets and execution
throughput.</p>
<p>A simplified CPU contains a program counter (PC), instruction-fetch
logic, decoder, register file, arithmetic and logic units (ALUs),
load/store logic and control circuitry. The PC identifies the next
instruction in the architectural execution model. A register file holds
operands and results. Execution units perform operations such as
addition, comparison or shifts, while memory instructions transfer
values between registers and addressed memory.</p>
<p>Modern cores may contain separate execution units for integers,
floating point and vectors. Their memory hierarchy can include
translation caches and multiple data or instruction cache levels. Not
every instruction uses every component. Interrupts and exceptions may
redirect control flow; privileged mechanisms let the operating system
handle events while restricting access from ordinary programs. The
diagram is a conceptual path, not a universal physical layout.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="PC + fetch → Decode &amp; registers
→ ALU / load-store → Write result" class="flow"><li>PC + fetch</li><li>Decode &amp; registers</li><li>ALU / load-store</li><li>Write result</li></ol></figure>
<p><strong>Register operation:</strong> In RISC-V, add x7, x5, x6 reads
registers x5 and x6, sums the values modulo the register width, and
writes x7. No data-memory load is implied by this instruction.</p>

<h3 id="cpu-architectural-state-and-register-roles">09.2 CPU
architectural state and register roles</h3>
<p>Architectural state is the information needed to describe the
program-visible progress of a processor. It includes general registers,
an instruction address and any other state defined by the ISA.
Privileged execution adds control registers and status fields used for
exceptions, interrupts and memory protection.</p>
<p>A register can have a conventional software role even if the hardware
treats it as a general-purpose register. Calling conventions assign
registers for arguments, return values and temporary storage. In RISC-V,
x0 is architecturally zero, whereas other roles such as stack pointer x2
arise from the ABI convention. The distinction matters when reading
assembly.</p>

<h3 id="instruction-decoding-and-datapath-controls">09.3 Instruction
decoding and datapath controls</h3>
<p>An instruction word encodes an operation and its operands. A decoder
examines fields such as opcode and function bits and determines which
functional units and register addresses are needed. The decoder may
generate direct control signals or translate the instruction into
internal operations, depending on the implementation.</p>
<p>A datapath contains the registers, arithmetic units, multiplexers and
wires through which operand values travel. Control logic selects inputs,
determines an operation and decides whether a result is written.
Separating control from data makes the design easier to reason about,
even though both are ultimately circuits on the chip.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Instruction bits → Decode controls

<p><strong>Choose an ALU input:</strong> For ADDI x5,x6,12, one ALU
input receives x6 and the other receives a sign-extended immediate. For
ADD x5,x6,x7, the second input instead receives x7. A multiplexer can
implement that selection in a simple datapath.</p>

<h3 id="isa-design-x86-64-arm-and-risc-v">09.4 ISA design: x86-64, Arm
and RISC-V</h3>
<p>An ISA defines the software-visible machine, not a particular core
design. x86-64 has variable-length instruction encodings and a long
compatibility history. AArch64 uses fixed 32-bit instruction encodings.
The RISC-V base integer ISA uses 32-bit instructions, with optional
compressed 16-bit encodings and other extensions.</p>
<p>A load-store architecture restricts ordinary arithmetic to registers
and uses separate memory-access instructions. Other ISAs can express
memory operands in some arithmetic instructions. Modern implementations
of different ISAs may nevertheless use similar internal techniques such
as multiple execution units and caches. Neither instruction count nor
instruction length alone determines performance.</p>

<h2 id="chapter-10">10. A real RISC-V instruction, bit by bit</h2>
<p>RV32I is a base integer instruction set with 32 architectural integer
registers, x0 through x31. Register x0 always reads as zero; writes to
it do not change its value. Most base instructions are 32 bits wide.
Optional extensions can introduce other operations and, in the
compressed extension, shorter instruction encodings.</p>
<p>For an R-type ADD instruction, bits 31:25 specify funct7, 24:20 rs2,
19:15 rs1, 14:12 funct3, 11:7 rd and 6:0 opcode. For add x7,x5,x6, the
fields are 0000000, 00110, 00101, 000, 00111 and 0110011. Combining them
yields 0x006283B3. This hexadecimal word is an instruction, not the same
thing as its byte sequence in a little-endian memory representation.</p>
<p>Suppose x5 = 7 and x6 = 5. The fetch mechanism obtains the
instruction, decode recognizes ADD and the register indices, operands
enter an execution unit, and the result 12 becomes the new architectural
value of x7. For this ordinary instruction, execution proceeds to the
next sequential address. A real superscalar processor may overlap these
actions with other instructions, but must preserve the specified
architectural behavior.</p>

<h3 id="risc-v-load-and-store-instructions">10.2 RISC-V load and store
instructions</h3>
<p>In the RV32I load-store model, memory is accessed by dedicated
instructions. A load computes an effective address from a base register
plus a sign-extended immediate, reads the specified width, and writes a
register result. Byte and halfword loads can sign-extend or zero-extend
depending on their opcode variant.</p>
<p>A store also computes an effective address but writes data from a
source register instead of producing a destination-register result.
Access permissions, alignment and the execution environment can
influence whether an operation completes or raises an exception. The
meaning of the memory bytes depends on the selected access width and
byte order.</p>

<h3 id="branches-jumps-and-loops">10.3 Branches, jumps and loops</h3>
<p>A conditional branch tests a relationship between register values and
chooses whether the next instruction address is a target or the normal
sequential address. RISC-V includes equality and signed or unsigned
ordering comparisons. Branch immediates encode PC-relative offsets with
an alignment constraint.</p>
<p>Unconditional jumps transfer control without a condition. JAL also
writes a link address to a destination register, which can support
function calls. JALR calculates a target using a register and immediate,
enabling returns and indirect calls. A loop is not a special physical
structure: it is a sequence of instructions whose control flow returns
to an earlier address.</p>

<p><strong>Loop invariant:</strong> Set x5 = 3 and x6 = 0. At each

<h3 id="function-calls-and-the-stack-convention">10.4 Function calls and
the stack convention</h3>
<p>A calling convention defines how separately compiled functions
exchange arguments and results and which registers must be preserved. A
caller can use call-clobbered registers freely but must save any needed
values across a call. A callee must restore callee-preserved registers
it changes. Leaf functions may need no stack frame.</p>
<p>A stack is a memory region used for per-call storage, such as saved
registers and local values that cannot remain in registers. Return
addresses may stay in a link register until a nested call makes saving
necessary. Stack alignment and layout are ABI requirements, not
universal properties of all CPUs or languages.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Caller arguments → Call / link →
Callee work → Restore and return" class="flow"><li>Caller arguments</li><li>Call / link</li><li>Callee work</li><li>Restore and return</li></ol></figure>
<p><strong>Nested calls:</strong> Function f calls g, and g calls h. If
g overwrites its link register when calling h, it must preserve its
original return address somewhere first, commonly in its stack frame.
Otherwise it cannot reliably return to f.</p>

<h2 id="chapter-11">11. Pipelining, speculation and parallel
execution</h2>
<p>A common educational pipeline divides instruction handling into
fetch, decode, execute, memory access and writeback. Each stage can work
on a different instruction. Once filled, an ideal single-issue pipeline
may complete one instruction per cycle, even though an individual
instruction takes several stages. Real pipelines experience hazards and
stalls.</p>
<p>Data hazards arise when an operation depends on an earlier result.
Forwarding can route a result directly to a consumer; some dependencies
require waiting. Structural hazards occur when operations compete for a
resource. Control hazards occur when the next instruction address
depends on a branch. Branch prediction guesses the path early; a wrong
prediction requires discarding or correcting speculative work. Modern
processors may execute operations out of program order when dependencies
permit and retire results in a way consistent with architectural
rules.</p>
<p>Multiple cores execute independent instruction streams, and
simultaneous multithreading shares core resources between hardware
threads. SIMD instructions apply one operation across several data
elements. None of these mechanisms guarantees a fixed speedup:
parallelism, dependency chains, memory traffic, branch behavior and
workload balance determine what can be achieved. Speculation also has
security implications because microarchitectural traces may persist even
when architectural results are discarded.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Fetch → Decode → Execute → Memory /
retire" class="flow"><li>Fetch</li><li>Decode</li><li>Execute</li><li>Memory /
retire</li></ol></figure>
<p><strong>Ideal pipeline example:</strong> For five stages and ten
independent instructions, an ideal one-instruction-per-cycle pipeline
needs 5 + 10 - 1 = 14 cycles, compared with 50 cycles if every
instruction occupies all five stages serially. This ignores hazards and
overhead.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 9" href="#ref-9">9</a></p>

values. Overlapping instructions increases the number completed per unit
time, even if an individual instruction still passes through every
stage.</p>
<p>Real CPUs may have more stages, multiple instructions in each stage
or specialized paths. The five-stage model illustrates the difference
between latency and throughput, not a universal CPU layout. Hazards
arise when instructions need the same resources, depend on previous
results or change the expected control flow.</p>

reduce the ideal gain.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 32" href="#ref-32">32</a></p>
<h3 id="data-hazards-forwarding-and-stalls">11.3 Data hazards,
forwarding and stalls</h3>
<p>A read-after-write dependency occurs when an instruction needs a
value produced by an earlier instruction. A simple pipeline can forward
an available result directly to a dependent execution stage rather than
waiting for the register file write. Not every result is available early
enough to avoid a stall.</p>
<p>Structural hazards arise when two operations compete for a hardware
resource. Control hazards arise when a branch changes the instruction
stream. Hardware interlocks can delay instructions until conditions are
safe. More advanced processors dynamically schedule ready instructions,
while preserving architecturally required results and ordering.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Producer executes → Result
forwarding → Consumer executes → Commit" class="flow"><li>Producer executes</li><li>Result
forwarding</li><li>Consumer executes</li><li>Commit</li></ol></figure>
<p><strong>Load-use hazard:</strong> Suppose LW x5,0(x6) is followed by
ADD x7,x5,x8. In a classic five-stage teaching design, the load’s data
is available after memory access, too late for the following
instruction’s normal execute stage. One stall may be needed even with
forwarding; actual cores differ.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 32" href="#ref-32">32</a></p>
<h3 id="out-of-order-execution-and-branch-prediction">11.4 Out-of-order
execution and branch prediction</h3>
<p>An out-of-order processor can execute independent instructions while
an older one is waiting for a resource. Register renaming maps
architectural names to physical storage to avoid certain false
dependencies. Scheduling logic issues ready operations, and retirement
machinery makes results architecturally visible in the required
order.</p>
<p>Branch prediction estimates control flow so the front end can
continue obtaining instructions. Speculative operations may be discarded
if a prediction proves incorrect. Such speculation can improve
throughput but consumes energy and creates security considerations. The
prediction mechanism does not change the program’s specified branch
condition.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Fetch and predict → Rename /
schedule → Execute ready work → Retire results" class="flow"><li>Fetch and predict</li><li>Rename /
schedule</li><li>Execute ready work</li><li>Retire results</li></ol></figure>
<p><strong>Illustrative branch penalty:</strong> With 20% branch
instructions, 5% mispredictions among branches and a 12-cycle penalty,
the average added cost is 0.20 x 0.05 x 12 = 0.12 cycles/instruction in
a simplified additive model. Real penalties can overlap other
delays.</p>

<h2 id="chapter-12">12. Registers, caches, DRAM and locality</h2>
<p>A memory hierarchy balances capacity, cost, bandwidth and access
latency. Registers are small and directly named by instructions. SRAM
caches hold copies of blocks from lower memory levels. DRAM provides
larger main memory, using charge-based storage cells that require
periodic refresh. Persistent storage offers much greater capacity but is
normally far slower than CPU-local memory for individual accesses.</p>
<p>Caches exploit temporal locality (recently used data may be reused)
and spatial locality (nearby data may be needed soon). An address is
interpreted using a block offset, an index or set selection, and a tag.
A cache hit finds the requested block; a miss triggers a lookup or
transfer from another level. Associativity and replacement choices
influence which blocks remain. Write-through and write-back policies
govern when stores reach the next level.</p>
<p>Shared-memory multiprocessors use coherence mechanisms so cores can
coordinate cached copies of a memory location. Coherence is distinct
from the memory consistency model, which constrains observable ordering
of operations across addresses. Software synchronization is still
required for safely sharing mutable data. Cache sizes and access times
are implementation-specific; no single latency table describes all
computers.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Registers → L1 / L2 / L3 → DRAM →
Persistent storage" class="flow"><li>Registers</li><li>L1 / L2 / L3</li><li>DRAM</li><li>Persistent storage</li></ol></figure>
<p><strong>Average memory access time:</strong> With a 1 ns cache
lookup, 5% miss rate and 80 ns additional miss penalty, AMAT = 1 + 0.05
x 80 = 5 ns. These are illustrative assumptions, not measurements of a
specific CPU.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 10" href="#ref-10">10</a></p>
<h3 id="sram-dram-and-the-memory-controller">12.2 SRAM, DRAM and the
memory controller</h3>
<p>SRAM commonly retains a bit using a feedback circuit as long as power
remains available. DRAM represents bits with stored charge that
gradually leaks, requiring periodic refresh. SRAM cells generally occupy
more area per bit, so SRAM is useful for relatively small fast memories
while DRAM is economical for larger main memory. Both are volatile in
their ordinary forms.</p>
<p>A DRAM controller schedules commands across channels, ranks and
banks. Activating a row makes its contents available in a row buffer;
subsequent column accesses may reuse that open row. A different row in
the same bank can require additional operations. Timing constraints,
refresh and competing requests determine observed latency.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="CPU request → Memory controller →
Select bank / row → Return data" class="flow"><li>CPU request</li><li>Memory controller</li><li>Select bank / row</li><li>Return data</li></ol></figure>
<p><strong>Row locality:</strong> Reading consecutive locations that
reside in the same open DRAM row may avoid repeated row activations. The
exact mapping of addresses to banks and rows is
implementation-dependent; sequential access alone does not guarantee a
particular timing.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 10" href="#ref-10">10</a>, <a aria-label="Reference 11" href="#ref-11">11</a></p>
<h3 id="cache-mapping-tags-and-replacement">12.3 Cache mapping, tags and
replacement</h3>
<p>A cache stores copies of selected memory blocks. A line typically
contains multiple adjacent bytes, a tag and status bits. In a
set-associative cache, address bits identify a set, while tags
distinguish possible blocks in that set. The number of ways limits how
many different blocks can coexist there.</p>
<p>A hit supplies data from the cache; a miss requires obtaining the
block from another level. Replacement policies choose a line to evict
when space is needed. Write-back caches can retain modified data until a
writeback, while write-through designs propagate writes sooner. Policies
differ across implementations.</p>

<h3 id="locality-miss-cost-and-prefetching">12.4 Locality, miss cost and
prefetching</h3>
<p>Temporal locality means recently accessed data is likely to be
accessed again. Spatial locality means nearby addresses are likely to be
accessed. Caches exploit both by retaining recent lines and fetching
multiple adjacent bytes on misses. A data structure that scatters nodes
can be less cache-friendly than contiguous arrays.</p>
<p>Hardware and software prefetchers try to bring data closer before
demand arrives. A useful prefetch hides part of access latency; an
inaccurate one wastes bandwidth or evicts useful data. Cache performance
is influenced by access patterns, working-set size, competition and the
number of outstanding requests.</p>

<h2 id="chapter-13">13. Virtual memory and address translation</h2>
<p>Programs generally operate on virtual addresses rather than directly
naming physical memory. Each process has a protected address space. A
memory management unit (MMU) translates virtual addresses using
operating-system-managed mapping structures and enforces access
permissions such as read, write, execute and user accessibility.</p>
<p>Paging divides virtual and physical memory into fixed-size units.
With 4 KiB pages, the low twelve address bits form the offset. The
remaining bits select a virtual page; page-table entries identify the
physical frame and relevant attributes. A translation lookaside buffer
(TLB) caches translations, reducing the need to traverse page tables for
each reference. Page-table structure and supported page sizes depend on
the architecture.</p>
<p>When a mapping is missing or an access violates permissions, the
processor can raise a page fault. The operating system may allocate a
page, load file-backed contents, restore a swapped page, or reject the
access. A page fault does not necessarily mean disk I/O. Virtual memory
enables isolation, sharing, sparse mappings and demand allocation. It
does not give a computer unlimited physical memory; heavy swapping can
sharply reduce responsiveness.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Virtual address → TLB / page table
→ Physical frame → Memory access" class="flow"><li>Virtual address</li><li>TLB / page table</li><li>Physical frame</li><li>Memory access</li></ol></figure>
<p><strong>4 KiB page example:</strong> Virtual address 0x12345 has page
number 0x12 and offset 0x345. If page 0x12 maps to frame 0xAB, the
translated physical address is 0xAB345 (assuming this simplified mapping
and page size).</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 10" href="#ref-10">10</a>, <a aria-label="Reference 11" href="#ref-11">11</a></p>
<h3 id="address-spaces-pages-and-page-tables">13.2 Address spaces, pages
and page tables</h3>
<p>Virtual memory gives a process an address space whose addresses need
not directly identify physical memory. A memory management unit
translates virtual page numbers using mappings controlled by privileged
software. The offset within a normal page remains the same after
translation. Permissions can restrict reading, writing or executing.</p>
<p>Page tables organize mappings in memory, often as multiple levels so
unused address ranges do not need full tables. A translation lookaside
buffer caches recent translations. A TLB miss can trigger a hardware or
software page-table walk depending on the architecture. It is different
from a missing or disallowed mapping, which can cause a fault.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Virtual address → TLB lookup →
Page-table walk if needed → Physical address" class="flow"><li>Virtual address</li><li>TLB lookup</li><li>Page-table walk if needed</li><li>Physical address</li></ol></figure>
<p><strong>Page offset:</strong> With 4 KiB pages, 0x12345 has virtual
page number 0x12 and offset 0x345. If that page maps to physical frame
0xAB, the physical address is 0xAB345, assuming the mapping allows the
operation.</p>

<h3 id="page-faults-demand-paging-and-copy-on-write">13.3 Page faults,
demand paging and copy-on-write</h3>
<p>An access to an unmapped or protected virtual page can cause a
processor exception. The kernel examines the cause and its own
memory-management metadata. Some faults are expected, such as first
access to a lazily allocated page; others indicate an invalid operation.
The kernel may arrange a mapping, load data or terminate the offending
operation.</p>
<p>Copy-on-write lets mappings initially share underlying pages while
preventing direct modification. When a permitted logical writer attempts
a write, the kernel can allocate a private copy and update the mapping.
This can avoid copying memory that will never be changed. The
optimization still requires careful accounting and synchronization.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Write to shared page → Protection
fault → Allocate and copy → Resume write" class="flow"><li>Write to shared page</li><li>Protection
fault</li><li>Allocate and copy</li><li>Resume write</li></ol></figure>
<p><strong>Cost of lazy allocation:</strong> A program reserves 100 MiB
of virtual address space but touches one 4 KiB page. Depending on OS
policy, most of the reserved range may not yet need physical data pages.
Reservation, commitment and residency are distinct concepts.</p>
<p class="sources">Sources: <a aria-label="Reference 10" href="#ref-10">10</a>, <a aria-label="Reference 11" href="#ref-11">11</a></p>
<h3 id="memory-pressure-swap-and-working-sets">13.4 Memory pressure,
swap and working sets</h3>
<p>A working set is the collection of memory pages actively needed over
some interval. If active working sets exceed available RAM, the OS must
reclaim pages. Clean file-backed pages can often be discarded and reread
later; modified pages may require writeback. Anonymous memory may be
moved to swap or handled by another policy.</p>
<p>Excessive page movement can cause thrashing: much time is spent
retrieving and replacing pages rather than performing useful work. More
virtual address space does not create more physical RAM. Memory
compression, reclaim heuristics and process limits can help, but no
mechanism removes the underlying capacity constraint.</p>

<h2 id="chapter-14">14. SSDs, hard disks and file systems</h2>
<p>A hard disk uses rotating magnetic media and movable heads. Its
access time depends partly on seeking and rotation, so sequential access
and random access have different costs. NAND flash stores information
through charge-related cell states and has no moving mechanical head. It
is read and programmed in pages and erased in larger blocks; details
vary by flash design.</p>
<p>An SSD controller maps logical block addresses to physical flash
locations using a flash translation layer. Wear leveling distributes
writes; garbage collection reclaims blocks; error-correction codes help
recover data. The operating system can inform the device that certain
logical blocks are no longer in use through discard mechanisms. NVMe is
a storage command protocol commonly used over PCI Express; it is not
itself the flash medium. Queues permit multiple outstanding
commands.</p>
<p>A file system builds names, directories, metadata, access rules and
allocation structures on top of storage. Journaling or copy-on-write
techniques can help maintain consistency after interruptions, but their
exact guarantees vary. A successful write call may mean the operating
system accepted bytes into a cache, not that they survived a power
failure. Applications that need durability must use appropriate
synchronization and understand the guarantees of the entire storage
stack.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="File operation → File system →
Block driver → Storage controller" class="flow"><li>File operation</li><li>File system</li><li>Block driver</li><li>Storage controller</li></ol></figure>
<p><strong>Why backup matters:</strong> A file system may recover its
metadata after a crash yet still lose recently modified application
data. Backups protect against a different class of failures and should
be independently restorable.</p>
<p class="sources">Sources: <a aria-label="Reference 10" href="#ref-10">10</a>, <a aria-label="Reference 12" href="#ref-12">12</a>, <a aria-label="Reference 29" href="#ref-29">29</a></p>
<h3 id="magnetic-disks-flash-and-block-interfaces">14.2 Magnetic disks,
flash and block interfaces</h3>
<p>A hard disk stores information magnetically on rotating platters.
Access requires positioning heads and waiting for the desired sector to
rotate beneath them. Sequential transfers can amortize these positioning
costs. Solid-state storage has no rotating media but still has
controller, flash-access and interface delays.</p>
<p>NAND flash is generally read and programmed at page granularity and
erased in larger blocks. Updates often require writing elsewhere and
reclaiming old locations later. The SSD controller exposes a logical
block interface so software need not manage every physical flash page
directly. NVMe defines a command interface designed for nonvolatile
storage over suitable transports.</p>

<h3 id="ssd-translation-garbage-collection-and-endurance">14.3 SSD
translation, garbage collection and endurance</h3>
<p>A flash translation layer maintains a mapping from host-visible block
addresses to physical flash locations. New writes may replace a mapping
rather than overwrite the original physical page. Old pages become
invalid, and garbage collection copies still-valid pages before erasing
a block for reuse.</p>
<p>Wear leveling spreads erase cycles across the available flash.
Overprovisioning provides extra physical capacity to assist management.
Write amplification describes how much physical writing occurs relative
to host writing. A discard or TRIM command can tell a device that
logical blocks no longer contain data the host needs, subject to device
and OS behavior.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Host write → Allocate new page →

<p><strong>Write amplification:</strong> If a host writes 10 GiB and the
SSD internally programs 15 GiB while doing relocation, the illustrative
write amplification is 1.5. It depends on workload, free space,
controller design and measurement interval.</p>

<h3 id="file-systems-journaling-and-durability">14.4 File systems,
journaling and durability</h3>
<p>A file system organizes persistent blocks into named files,
directories and metadata. Many designs use structures such as inodes or
allocation tables to record ownership, permissions and block locations.
The OS can cache file contents in memory and defer storage writes to
improve throughput.</p>
<p>Crash consistency concerns what remains structurally valid after
unexpected interruption. Journaling records selected changes in a log so
recovery can replay or discard transactions according to the format.
Copy-on-write file systems use other approaches. Neither technique
automatically guarantees that the most recent application data has
reached durable storage; application synchronization and device
guarantees matter.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Application write → Page cache →
File-system transaction → Persistent media" class="flow"><li>Application write</li><li>Page cache</li><li>File-system transaction</li><li>Persistent media</li></ol></figure>
<p><strong>Save a document safely:</strong> An editor can write a
temporary file, request appropriate synchronization, then rename it over
the destination. Exact crash-durability guarantees depend on the file
system and whether relevant file and directory metadata are
synchronized. A successful write call alone is not a universal
durability guarantee.</p>

<h2 id="chapter-15">15. Motherboards, interconnects and
input/output</h2>
<p>The motherboard or system-on-chip connects computation, memory,
storage and peripherals. Modern CPUs often integrate memory controllers
and some PCI Express lanes. A platform controller or equivalent fabric
may connect additional devices. Clock generation, voltage regulation and
thermal management keep components within operating requirements. A
system-on-chip combines many of these functions on a die or package.</p>
<p>Interconnects transfer information according to electrical and
protocol rules. DDR memory channels link controllers to DRAM; PCI
Express provides packet-based point-to-point links; USB connects many
external peripherals. Bus widths, lane counts, encoding overhead,
protocol revisions and device behavior affect usable bandwidth. Faster
advertised link speeds do not automatically imply faster
applications.</p>
<p>Device drivers program controllers using mechanisms such as
memory-mapped I/O. Interrupts notify a CPU of events; polling checks
status repeatedly. Direct memory access (DMA) lets a device move data to
or from memory without the CPU copying every byte. The CPU and driver
still configure transfers, handle completion and maintain appropriate
synchronization. An IOMMU can translate and restrict device-visible
addresses, supporting isolation and virtualization.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Application → Driver / kernel →
Controller + DMA → Device" class="flow"><li>Application</li><li>Driver / kernel</li><li>Controller + DMA</li><li>Device</li></ol></figure>
<p><strong>Receiving network data:</strong> A network adapter can place
received packets into configured memory buffers using DMA. Completion is
reported by an interrupt or polling mechanism, after which the OS
network stack processes the data.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 13" href="#ref-13">13</a></p>
<h3 id="motherboard-power-clocks-and-platform-topology">15.2 Motherboard
power, clocks and platform topology</h3>
<p>A motherboard connects processors, memory, storage, external
interfaces and power-delivery components. Voltage regulators supply
suitable low-voltage power rails to chips. Clock sources and
clock-distribution circuits support communication and internal timing.
On many modern platforms, functions once assigned to separate chipset
components are integrated into the processor package.</p>
<p>The topology determines which devices connect directly to the CPU or
through other controllers. Some communication paths share bandwidth;
others have dedicated links. A physical connector does not by itself
reveal all electrical capabilities. Board layout, firmware
configuration, processor support and device capabilities jointly
determine the usable system.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Power and clocks → CPU / SoC →
Memory and PCIe → Peripheral controllers" class="flow"><li>Power and clocks</li><li>CPU / SoC</li><li>Memory and PCIe</li><li>Peripheral controllers</li></ol></figure>
<p><strong>Shared bandwidth:</strong> Two devices behind a shared
upstream link can contend for that link when both transfer at once.
Their individual advertised speeds do not prove that the system can
sustain both at maximum speed simultaneously.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 13" href="#ref-13">13</a></p>
<h3 id="pci-express-usb-and-interconnect-bandwidth">15.3 PCI Express,
USB and interconnect bandwidth</h3>
<p>PCI Express is a packet-based interconnect with point-to-point links.
A link may contain multiple lanes, and supported signaling generations
determine raw transfer rates. Negotiated link width and speed depend on
both endpoints and the physical path. Protocol overhead reduces useful
application throughput below raw signaling capacity.</p>
<p>USB defines a family of host-device communication mechanisms.
Connector shapes, supported signaling modes, power delivery and device
functionality are separate characteristics. A particular connector may
support multiple modes or only a subset. Device discovery and drivers
allow the OS to communicate through these protocols.</p>

<h3 id="interrupts-dma-and-device-queues">15.4 Interrupts, DMA and
device queues</h3>
<p>Interrupts notify processors of events such as completed I/O or
timers. Polling is another strategy: software checks a status source
repeatedly. Interrupts can reduce idle checking, while polling can
sometimes be useful for high event rates or predictable latency. A
device driver chooses a strategy appropriate to the interface.</p>
<p>Direct memory access lets capable devices transfer data without a CPU
executing each individual byte copy. Drivers arrange buffers and
mappings, submit descriptors and handle completion. An IOMMU can
constrain device-visible addresses, helping isolate DMA. Cache
synchronization and ownership rules matter on systems that are not fully
coherent.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Driver submits descriptor → Device
transfers data → Completion event → Driver releases buffer" class="flow"><li>Driver submits descriptor</li><li>Device
transfers data</li><li>Completion event</li><li>Driver releases buffer</li></ol></figure>
<p><strong>Receive a network frame:</strong> A NIC may place received
bytes into a driver-provided buffer using DMA and signal completion. The
CPU then processes protocol headers and hands relevant data to software.
It need not execute a separate copy instruction for each byte arriving
on the wire.</p>

<h2 id="chapter-16">16. What happens when power is switched on?</h2>
<p>Power supplies and voltage regulators establish the rails needed by
hardware. Reset logic holds parts of the system in known initial
conditions until requirements are met. On reset, a processor begins
execution according to its architecture and platform design, typically
from firmware stored in nonvolatile memory or mapped into its address
space.</p>
<p>Firmware initializes essential components, including enough memory
and device support to locate and execute the next stage. On many modern
PCs, UEFI supplies standardized interfaces for boot applications and
drivers. Its boot manager chooses a configured boot target, often an
operating-system loader stored in an EFI system partition. Secure Boot,
when enabled and correctly configured, verifies authorized images
according to its trust policy. Other platforms may use very different
firmware chains.</p>
<p>The loader prepares the operating-system kernel and any required
startup data, then transfers control. The kernel initializes memory
management, scheduling, interrupt handling and device drivers. It mounts
or locates the root file system and launches the initial user-space
process. Services start and a login screen or graphical desktop may
appear. Embedded devices sometimes boot directly into an application or
a real-time operating system, without a desktop.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Power + reset → Firmware → OS
loader → Kernel + services" class="flow"><li>Power + reset</li><li>Firmware</li><li>OS
loader</li><li>Kernel + services</li></ol></figure>
<p><strong>Firmware versus OS:</strong> Firmware prepares and hands off
the platform; the operating system manages ongoing resource use. Some
firmware interfaces remain available after boot, but they do not replace
the OS kernel.</p>
<p class="sources">Sources: <a aria-label="Reference 14" href="#ref-14">14</a>, <a aria-label="Reference 15" href="#ref-15">15</a></p>
<h3 id="reset-firmware-and-hardware-initialization">16.2 Reset, firmware
and hardware initialization</h3>
<p>After power and reset conditions are established, a processor begins
from architecture-defined initial state and an implementation-specific
startup environment. Firmware performs early setup, which can include
memory training, device discovery and configuration. Some platforms
contain several independent controllers with their own firmware.</p>
<p>Firmware bridges the hardware’s initial conditions and the
environment expected by later software. It may initialize memory before
ordinary application code can use it. Recovery mechanisms and
authenticated updates reduce the risk of firmware corruption. Exact
startup stages vary among desktop computers, embedded systems and
phones.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Stable power → Processor reset →
Early firmware → Initialized platform" class="flow"><li>Stable power</li><li>Processor reset</li><li>Early firmware</li><li>Initialized platform</li></ol></figure>
<p><strong>Why RAM may need training:</strong> A memory interface must
sample high-speed signals at suitable times. Startup training can adjust
parameters to account for physical properties of the platform. A failed
initialization can prevent the machine from reaching its normal boot

<h3 id="uefi-bootloaders-and-the-kernel-handoff">16.3 UEFI, bootloaders
and the kernel handoff</h3>
<p>UEFI specifies interfaces between platform firmware and software that
runs in its environment. On a typical UEFI PC, a boot manager chooses a
configured boot option and loads an appropriate executable. The
bootloader can locate the operating-system kernel and associated boot
data, then prepare the environment for the kernel’s own
initialization.</p>
<p>A kernel establishes memory-management structures, interrupt handling
and drivers as needed. It can then initialize its file systems and start
the first user-space services. The details differ by operating system. A
bootloader is not generally the operating system itself, and firmware
services are not identical to ordinary system calls.</p>

<p><strong>Boot option versus partition:</strong> A firmware boot entry
may identify a particular executable on an EFI System Partition. The

<h3 id="secure-boot-measured-boot-and-recovery">16.4 Secure boot,
measured boot and recovery</h3>
<p>Secure boot uses a trust policy to decide whether selected boot
components are acceptable, commonly through signature verification. It
aims to prevent unauthorized startup code from executing in that chain.
The details depend on which components are covered and how keys and
revocation lists are managed.</p>
<p>Measured boot records cryptographic measurements of components,
potentially using a hardware trust module. Measurements can support
later attestation but do not necessarily block execution. Recovery
mechanisms help restore an acceptable firmware or boot image after
failure. Security relies on protecting update mechanisms, trust anchors
and configuration as well as verifying binaries.</p>

<h2 id="chapter-17">17. Operating systems: processes and system
calls</h2>
<p>An operating system provides abstractions over hardware, manages
shared resources and enforces protection boundaries. A process is a
running program context with an address space, resources and execution
state. Threads are execution streams within a process; they usually
share the process’s address space while having separate register
contexts and stacks.</p>
<p>A scheduler chooses runnable threads for available CPU cores. A timer
interrupt or another event can cause the kernel to reconsider which
thread should run. A context switch saves and restores relevant
execution state. The operating system balances responsiveness,
throughput, fairness, deadlines or other goals according to its
policies. A thread blocked on input does not need to consume CPU time
while it waits.</p>
<p>Ordinary applications operate with restricted privileges. A system
call requests a kernel service, for example reading a file, allocating
an address mapping or creating a process. Special instructions or
architecture-defined mechanisms enter the kernel, which validates the
request and returns results or errors. Exceptions report synchronous
events such as invalid memory references; interrupts are typically
asynchronous notifications. The kernel also manages drivers, networking,
memory and security checks.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="User program → System call → Kernel
service → Return to user" class="flow"><li>User program</li><li>System call</li><li>Kernel
service</li><li>Return to user</li></ol></figure>
<p><strong>Reading a file:</strong> A program requests bytes from an
open file. The kernel checks permissions and offsets, may use cached
pages or initiate device I/O, then returns available data or an error.
The calling thread may block while waiting.</p>

<h3 id="processes-threads-and-protected-execution">17.2 Processes,
threads and protected execution</h3>
<p>A process is an OS abstraction that associates executing code with
resources such as virtual memory and open files. A thread represents an
execution context with registers, instruction position and scheduling
state. Multiple threads in one process normally share an address space
but have their own stacks and execution contexts.</p>
<p>User mode restricts privileged operations; kernel mode permits the OS
to configure memory translation, interrupts and hardware resources. A
system call provides a controlled entry into kernel code. The kernel
validates relevant arguments and permissions before operating on shared
resources. A process boundary is useful for isolation but depends on
correct enforcement.</p>

<h3 id="scheduling-context-switches-and-cpu-time">17.3 Scheduling,

<p>A scheduler selects runnable execution contexts for available
processors. Workloads can be interactive, batch-oriented or subject to
real-time constraints. Scheduling policies trade off responsiveness,
throughput, fairness and deadlines. Waiting for disk or network I/O
usually removes a thread from the runnable set until it can
progress.</p>
<p>A context switch saves the execution state of one thread and restores
another. Some memory translation state may also change. Switching has
direct bookkeeping costs and indirect cache or TLB effects. On a
multicore system, each core can run its own context concurrently,
subject to shared-resource contention.</p>

<h3 id="system-calls-exceptions-and-device-services">17.4 System calls,
exceptions and device services</h3>
<p>System calls let applications request operations that require OS
mediation. A calling convention identifies the operation and arguments;
a dedicated instruction or equivalent mechanism transfers control to an
appropriate handler. The kernel validates user pointers, looks up
resource handles and applies access rules before returning a result or
error.</p>
<p>Exceptions arise synchronously from an instruction or execution
condition, while hardware interrupts are generally asynchronous relative
to program instructions. Both use architecture-defined control
transfers. The OS can resolve some conditions and resume execution,
deliver an error to the application or terminate it. Not every library
call requires a system call.</p>

system call with a file descriptor, buffer address and length. Cached
data may satisfy the request without physical disk access. If storage
I/O is needed, the calling thread may wait while the OS runs other
work.</p>

<h2 id="chapter-18">18. Concurrency, synchronization and
virtualization</h2>
<p>Concurrency means tasks make progress during overlapping time
periods. Parallelism means operations execute simultaneously on multiple
resources. A single core can interleave concurrent threads; several
cores may execute them at the same time. Shared mutable data introduces
races if access is not coordinated. A read-modify-write expression is
not necessarily one indivisible operation.</p>
<p>Locks protect critical sections, atomic operations provide specific
indivisible behaviors, and condition variables or message queues help
threads coordinate. Deadlock can occur when tasks wait cyclically for
resources. Memory ordering matters because compilers and processors can
reorder operations within allowed rules. Correct synchronization gives
the guarantees needed for communication; simply adding a delay is not
reliable.</p>
<p>Virtual machines run guest operating systems with virtual hardware
under a hypervisor. Hardware virtualization extensions help trap or
manage privileged operations and translate guest memory. Containers
instead typically isolate applications through operating-system
mechanisms while sharing the host kernel. They are not identical
security boundaries, and neither model automatically makes a workload
secure. Emulation may translate or interpret instructions for another
architecture, often with additional cost.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Threads → Synchronization → Shared
resources → Correct results" class="flow"><li>Threads</li><li>Synchronization</li><li>Shared
resources</li><li>Correct results</li></ol></figure>
<p><strong>Lost update:</strong> Two threads read counter = 10, each
computes 11, and both store 11. The intended result of two increments is
12. A suitable atomic increment or lock prevents this particular
race.</p>

<h3 id="race-conditions-atomics-and-mutual-exclusion">18.2 Race
conditions, atomics and mutual exclusion</h3>
<p>A race condition occurs when a result depends on the relative timing
of concurrent operations. A data race has a more specific meaning in
language memory models, often involving conflicting unsynchronized
accesses. Even a simple increment may involve multiple machine
operations: load, add and store.</p>
<p>A mutex provides mutual exclusion for a critical section. Atomic
operations provide indivisible behavior with specified ordering
guarantees, but an atomic variable does not automatically make an entire
multi-step algorithm correct. The synchronization design must protect
invariants across every relevant access path. Memory ordering rules vary
by language and architecture.</p>

<h3 id="condition-variables-deadlocks-and-progress">18.3 Condition
variables, deadlocks and progress</h3>
<p>A condition variable lets a thread wait for a predicate on shared
state while releasing its associated lock. The predicate must be
rechecked after waking because another thread can change it before the
waiter proceeds, and some interfaces allow spurious wakeups. A semaphore
maintains permits for controlling access or counting events.</p>
<p>Deadlock occurs when participants cannot proceed because they wait
for one another. A common case involves two locks acquired in
inconsistent order. Starvation differs: a thread could theoretically
proceed but continually loses access to resources. Livelock involves
repeated changes without useful progress. Correct concurrent algorithms
reason about both safety and progress.</p>

<h2 id="chapter-19">19. From source code to executable instructions</h2>
<p>A compiler translates a program from a source representation into
another form. In a typical native compiler, lexical analysis identifies
tokens, parsing constructs syntax, and semantic analysis checks meaning
and types. Intermediate representations make program transformations
easier. Optimization can simplify computations, remove dead code or
improve instruction selection while preserving the language’s required
behavior.</p>
<p>A backend selects target instructions, allocates registers and emits
assembly or object code. An assembler encodes instructions and creates
object-file sections and relocation information. A linker combines
objects and libraries, resolves symbols and constructs an executable or
shared library. At launch, an OS loader maps executable segments, sets
up the execution environment and may involve a dynamic linker. A calling
convention defines how functions exchange arguments, results and
preserved registers.</p>
<p>Interpreters and virtual machines offer other execution models.
CPython normally compiles source to bytecode that its interpreter
executes; exact bytecode depends on the implementation and release.
Just-in-time compilers generate machine code during execution, sometimes
specializing code using runtime observations. Many environments combine
interpretation, native code and runtime services. Ultimately, all
software execution relies on physical hardware performing
operations.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Source + parser → IR + optimizer →
Machine code → Link / load" class="flow"><li>Source + parser</li><li>IR + optimizer</li><li>Machine code</li><li>Link / load</li></ol></figure>
<p><strong>Inspect a tiny C function:</strong> For a file containing int
add(int a,int b){return a+b;}, clang -O2 -S add.c produces target
assembly. The exact output depends on target architecture, compiler
version and options.</p>

<h3 id="lexing-parsing-and-semantic-analysis">19.2 Lexing, parsing and
semantic analysis</h3>
<p>A compiler front end reads source text and turns characters into
tokens such as identifiers, keywords and operators. Parsing checks
grammatical structure and builds a representation such as an abstract
syntax tree. Semantic analysis resolves names, checks types and
validates language-specific rules that grammar alone cannot express.</p>
<p>The same token sequence can be invalid because a variable is
undeclared or an operation has incompatible types. Diagnostics should
explain these errors at meaningful source locations. The front end
establishes language behavior before later optimization or code
generation decisions are made. Interpreters often use similar front-end
techniques.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Source text → Token stream → Syntax
tree → Typed representation" class="flow"><li>Source text</li><li>Token stream</li><li>Syntax
tree</li><li>Typed representation</li></ol></figure>
<p><strong>Parse precedence:</strong> The expression 2 + 3 * 4 normally
parses as addition whose right operand is multiplication. Evaluating
this tree yields 14, not 20. Parentheses can change the tree to make
addition happen first.</p>

<h3 id="intermediate-representation-and-optimization">19.3 Intermediate
representation and optimization</h3>
<p>An intermediate representation (IR) expresses operations in a form
suited to analysis and transformation. A compiler may use multiple IRs
to bridge language-level constructs and machine-specific operations.
Control-flow graphs represent possible execution paths; data-flow
information tracks where values originate and where they are used.</p>
<p>Optimization aims to improve execution while preserving behavior
required by the language. Constant folding can replace a known
calculation; dead-code elimination can remove operations that cannot
affect observable behavior. Aliasing, exceptions, concurrency and
numeric semantics can restrict transformations. A faster transformation
that changes required results is not correct.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Typed source → Intermediate code →
Analysis and transforms → Lower-level IR" class="flow"><li>Typed source</li><li>Intermediate code</li><li>Analysis and transforms</li><li>Lower-level IR</li></ol></figure>
<p><strong>Constant folding:</strong> A compiler can replace 6 * 7 with
42 when language rules permit. It cannot generally remove an arbitrary
function call merely because its return value is unused: the call may
perform I/O, mutate state or raise an observable error.</p>

<h3 id="assembly-linking-loading-and-runtimes">19.4 Assembly, linking,
loading and runtimes</h3>
<p>A compiler back end selects target instructions, assigns registers
and schedules operations. An assembler converts assembly into machine
bytes and object-file metadata. A linker combines object files, resolves
symbol references and arranges sections. Some references remain for a
dynamic loader to resolve when the program starts or later.</p>
<p>The OS loader maps executable code and data into an address space and
prepares initial execution state. A language runtime may initialize
allocators, garbage collection, exceptions or other services before
calling the user’s main function. Bytecode interpreters and just-in-time
compilers provide alternative execution strategies; in every case,
physical CPUs ultimately execute machine instructions.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Compiler back end → Object files →
Linker → Loader and runtime" class="flow"><li>Compiler back end</li><li>Object files</li><li>Linker</li><li>Loader and runtime</li></ol></figure>
<p><strong>Unresolved symbol:</strong> One source file calls add(),
which is defined in another object file. The linker can resolve the
reference when both are included. If the definition is absent and no
suitable library supplies it, linking generally reports an unresolved
symbol.</p>

<h2 id="chapter-20">20. GPU rendering, displays and accelerators</h2>
<p>A GPU is designed to deliver high throughput across many similar
operations. Graphics workloads transform geometry, rasterize primitives
into fragments and compute pixel contributions using shader programs and
fixed-function units. A display engine ultimately reads image buffers
and transmits pixel information to a display, where electronics drive
visible output. Modern graphical desktops compose multiple window
surfaces into a final image.</p>
<p>General-purpose GPU computing uses many execution lanes and a
hierarchy of registers, shared or local storage and device memory.
NVIDIA CUDA organizes work into threads and blocks; groups of threads
execute using a SIMT model. Branch divergence, memory access patterns
and resource occupancy affect performance. A GPU is not automatically
faster than a CPU for sequential, small or transfer-heavy tasks.</p>
<p>Specialized AI accelerators may use matrix multiply units or other
dataflow engines. A systolic array passes operands and partial results
between arithmetic cells, reducing repeated transfers to distant memory.
The CPU often orchestrates these accelerators, preparing data and
launching work. Actual system performance depends on compute throughput,
memory bandwidth, interconnects, numerical precision and how efficiently
software maps the workload onto the hardware.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="CPU submits work → GPU executes →
Frame buffer → Display scan-out" class="flow"><li>CPU submits work</li><li>GPU executes</li><li>Frame buffer</li><li>Display scan-out</li></ol></figure>
<p><strong>Image parallelism:</strong> A brightness adjustment can
process millions of pixels independently, making it a good candidate for
vector or GPU execution. A short dependency-heavy control task may be
better handled on a CPU.</p>

<h3 id="raster-graphics-pixels-and-the-rendering-pipeline">20.2 Raster
graphics, pixels and the rendering pipeline</h3>
<p>A three-dimensional scene can be represented using vertices,
geometry, materials, lights and a camera. A graphics pipeline transforms
vertices from object coordinates toward screen coordinates, determines
which sample locations are covered by primitives, and calculates colors.
Depth testing and blending determine how visible fragments combine.
Modern graphics APIs expose programmable stages as well as
fixed-function operations.</p>
<p>The resulting image can be stored in a framebuffer, which is a memory
resource containing pixel data. A compositor may combine several windows
or surfaces before display. GPU rendering and display scanout are
distinct processes: a display controller can read a completed buffer
while rendering proceeds into another one.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Vertices → Transform and rasterize
→ Shade and blend → Framebuffer" class="flow"><li>Vertices</li><li>Transform and rasterize</li><li>Shade and blend</li><li>Framebuffer</li></ol></figure>
<p><strong>Frame budget:</strong> A 60 Hz target gives approximately
16.67 ms per frame. A 120 Hz target gives about 8.33 ms. Rendering,
synchronization, CPU work and display scheduling all contribute to
whether a frame is delivered on time.</p>
<p class="sources">Sources: <a aria-label="Reference 19" href="#ref-19">19</a>, <a aria-label="Reference 27" href="#ref-27">27</a></p>
<h3 id="gpu-execution-memory-and-parallel-work">20.3 GPU execution,
memory and parallel work</h3>
<p>GPUs use many execution resources to process large numbers of similar
operations. In a SIMT programming model, many logical threads execute
together in groups, with hardware coordinating their instructions. If
threads in a group choose different branches, the hardware may need to
execute different paths separately, reducing utilization.</p>
<p>A GPU memory hierarchy can include per-thread registers,
group-accessible scratchpad memory, caches and device memory.
Performance depends on arranging data accesses so useful bytes can be
transferred efficiently. Synchronization within groups and between
kernels has costs and rules. GPUs excel at highly parallel workloads,
but a serial dependency chain can limit the advantage.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Host launches work → Thread groups
→ Parallel arithmetic → Device memory result" class="flow"><li>Host launches work</li><li>Thread groups</li><li>Parallel arithmetic</li><li>Device memory result</li></ol></figure>
<p><strong>Vector addition:</strong> To compute C[i] = A[i] + B[i] for
one million elements, assign each element to one logical thread or
distribute several elements per thread. The additions are independent,
but every element still requires data movement, so memory bandwidth can
be the bottleneck.</p>
<p class="sources">Sources: <a aria-label="Reference 19" href="#ref-19">19</a>, <a aria-label="Reference 21" href="#ref-21">21</a></p>
<h3 id="display-scanout-input-lag-and-media-engines">20.4 Display
scanout, input lag and media engines</h3>
<p>A display refresh presents pixel data at a defined cadence or
according to a variable refresh protocol. A display controller typically
reads a framebuffer and sends a timed signal to the display. Pixel
response time, refresh timing and buffering are separate factors in the
overall experience.</p>
<p>A computer may also include dedicated video encode and decode units.
These handle supported compression formats more efficiently than a
general CPU or programmable GPU for many workloads. Support depends on
codec, profile, resolution and hardware generation. The decoded frames
still need memory and composition before presentation.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Input event → Application update →
Render / composite → Display refresh" class="flow"><li>Input event</li><li>Application update</li><li>Render / composite</li><li>Display refresh</li></ol></figure>
<p><strong>Framebuffer traffic:</strong> An uncompressed 3840 x 2160
buffer with four bytes per pixel contains 33,177,600 bytes. Reading that
buffer 60 times per second represents roughly 1.99 GB/s of raw pixel
data. Real display paths may use compression, multiple planes or
different formats.</p>

<h2 id="chapter-21">21. How the internet and a browser work</h2>
<p>The internet connects networks through packet forwarding. A browser
identifies a resource by its URL. It may resolve the domain through DNS,
establish or reuse a connection, authenticate an HTTPS endpoint through
TLS and issue an HTTP request. TCP supplies a reliable ordered byte
stream; QUIC provides secure multiplexed transport over UDP and is used
by HTTP/3. Actual behavior depends on cached results, protocol
negotiation and network configuration.</p>
<p>Routers forward IP packets toward their destinations. Link-layer
frames carry packets across individual links such as Ethernet or Wi-Fi.
Servers process requests and send responses; content delivery networks
and caches may serve resources nearer to the client. Different packets
can experience different delays, and bandwidth and round-trip time are
distinct performance properties.</p>
<p>After receiving HTML, the browser builds a document representation;
CSS rules contribute styling, and JavaScript can change the document or
request further resources. The rendering engine computes layout, paints
and composites visual content. The browser may use several processes and
threads for isolation and performance. GPU acceleration can help with
some rendering stages. The resulting screen depends on an entire chain
of software, network and hardware operations.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="DNS + connection → HTTP request →
HTML / CSS / JS → Layout + pixels" class="flow"><li>DNS + connection</li><li>HTTP request</li><li>HTML / CSS / JS</li><li>Layout + pixels</li></ol></figure>
<p><strong>Latency versus bandwidth:</strong> A 1 MB response on a 10
Mbit/s link needs at least about 0.8 seconds of ideal payload
transmission, excluding protocol overhead and latency. A fast link can
still feel slow if many round trips are required.</p>

<h3 id="network-addressing-routing-and-dns">21.2 Network addressing,
routing and DNS</h3>
<p>Networks send data across local links and interconnected routers. IP
addresses identify network-layer endpoints or interfaces, and routing
decisions select next hops toward destinations. Local link addresses
serve a different scope. A packet can traverse several networks whose
owners and physical media differ.</p>
<p>DNS maps domain names to records such as IP addresses and aliases. A
resolver can use cached answers or query other DNS infrastructure.
Records have time-to-live values that influence caching. A domain name
can resolve to different addresses over time or by location; an address
is not permanently tied to one human-readable name.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Domain name → DNS resolver → IP

<p><strong>Cache expiration:</strong> A DNS record with a 300-second TTL
can typically be reused within its remaining validity interval, subject
to resolver policy. After that interval a resolver may need to refresh
the answer. This is separate from a web browser’s HTTP response
cache.</p>

<h3 id="tcp-udp-quic-and-reliable-delivery">21.3 TCP, UDP, QUIC and
reliable delivery</h3>
<p>TCP provides an ordered byte stream with mechanisms for acknowledging
data, retransmitting losses and controlling sending behavior.
Applications frame their own messages within that stream. UDP provides
datagrams without TCP’s built-in reliable ordered stream semantics; an
application or higher-level protocol can add the behavior it needs.</p>
<p>QUIC operates over UDP and provides secure multiplexed streams with
transport-level loss recovery and congestion control. Independent
streams can reduce some cross-stream blocking compared with multiplexing
over one TCP byte stream. Network loss, path latency, congestion and
endpoint processing influence actual transfer speed regardless of
protocol choice.</p>

<h3 id="http-tls-and-the-browser-rendering-path">21.4 HTTP, TLS and the

<p>HTTP defines request and response semantics, including methods,
status codes and metadata. HTTPS adds a protected transport using TLS,
with certificate-based server authentication in typical browser
connections. Encryption protects data in transit between TLS endpoints;
it does not prove that a web application is trustworthy or bug-free.</p>
<p>After receiving resources, a browser parses HTML into a document
tree, processes style rules and executes scripts according to their
loading rules. Layout calculates geometry, painting describes visible
content, and compositing combines layers for display. Caching and
parallel resource loading can improve responsiveness, while slow scripts
or expensive layout can delay interaction.</p>

<h2 id="chapter-22">22. How artificial intelligence runs on
computers</h2>
<p>A neural network represents a parameterized mathematical function.
Training adjusts its parameters using data and an optimization
objective, commonly through gradients computed by backpropagation.
Inference evaluates a trained model on new inputs. Matrix
multiplications, reductions, nonlinear functions and memory operations
dominate many architectures, although the exact workload varies.</p>
<p>A language model commonly converts text into tokens, maps tokens to
numerical embeddings and applies repeated layers of attention and
feed-forward transformations. During autoregressive generation, it
predicts a distribution over possible next tokens, selects one according
to a decoding procedure and repeats. The system retains intermediate
state such as attention key/value caches to avoid repeating some
computation. Training is different from generating a response; ordinary
inference does not automatically update all model parameters.</p>
<p>GPUs, TPUs and NPUs can accelerate parts of this workload.
Lower-precision representations can reduce bandwidth and computation
cost, but may change accuracy or numerical behavior. Large models can be
constrained by memory capacity, communication and bandwidth as much as
by arithmetic. Machine learning does not change the physical foundations
of computers: it is software and numerical computation mapped onto
electronic hardware.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Input tokens → Numerical tensors →
Model layers → Output tokens" class="flow"><li>Input tokens</li><li>Numerical tensors</li><li>Model layers</li><li>Output tokens</li></ol></figure>
<p><strong>Matrix multiply:</strong> A 2 x 3 matrix multiplied by a 3 x
4 matrix produces a 2 x 4 result. Each output requires three products
and their sum. Large neural networks perform vast numbers of related
operations.</p>
<p class="sources">Sources: <a aria-label="Reference 19" href="#ref-19">19</a>, <a aria-label="Reference 20" href="#ref-20">20</a>, <a aria-label="Reference 30" href="#ref-30">30</a>, <a aria-label="Reference 31" href="#ref-31">31</a></p>
<h3 id="neural-networks-as-numerical-computation">22.2 Neural networks
as numerical computation</h3>
<p>A neural network is a parameterized mathematical function constructed
from operations on numerical arrays. A dense layer commonly computes a
weighted sum plus a bias, followed by an activation function. The input
and learned weights determine outputs; arithmetic operations run on
ordinary digital circuits or specialized matrix units.</p>
<p>Training adjusts parameters using a learning objective and an
optimization procedure. In gradient-based training, backpropagation
applies the chain rule to compute derivatives efficiently through the
computational graph. Inference uses trained parameters to evaluate the
network for new inputs, though some systems may perform additional
adaptation or search.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Input tensor → Weighted operations
→ Activation → Output tensor" class="flow"><li>Input tensor</li><li>Weighted operations</li><li>Activation</li><li>Output tensor</li></ol></figure>
<p><strong>Single artificial neuron:</strong> For input [2, 3], weights
[0.5, -1] and bias 0.2, the weighted sum is 1 - 3 + 0.2 = -1.8. A ReLU
activation maps this to 0. Different parameters and activation functions
produce different outputs.</p>

<h3 id="transformers-attention-and-token-generation">22.3 Transformers,
attention and token generation</h3>
<p>A transformer processes sequences using learned representations and
attention mechanisms. In scaled dot-product attention, projected query
and key vectors determine scores that are normalized and used to combine
value vectors. Multihead attention provides several learned projections,
while feed-forward layers and normalization contribute additional
transformations.</p>
<p>Many language models represent text using tokens and predict a
distribution for the next token. Generation repeatedly evaluates this
distribution and selects a token using a decoding rule. Cached key and
value tensors can reduce repeated computation for prior tokens. The
model’s outputs are generated from learned statistical patterns and
context; they are not guaranteed to be factually correct.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Token IDs → Embeddings and layers →
Next-token scores → Select next token" class="flow"><li>Token IDs</li><li>Embeddings and layers</li><li>Next-token scores</li><li>Select next token</li></ol></figure>
<p><strong>A tiny score vector:</strong> Suppose three candidate tokens
have probabilities 0.6, 0.3 and 0.1. Greedy decoding selects the first;
sampling can choose any according to its probability. This example omits
the much larger vocabulary and detailed decoding rules of a real
model.</p>

architectures. Specialized accelerators provide parallel
multiply-accumulate resources and organize data reuse to reduce
expensive memory traffic. GPUs and TPUs use different designs and
programming ecosystems, but both benefit from parallelizable tensor
operations.</p>
<p>Numeric formats trade precision, range, storage and arithmetic
throughput. Reduced-precision formats or quantization can reduce model
memory and improve speed, with potential accuracy effects depending on
the model and method. Training also needs intermediate activations,
gradients and optimizer state; inference may need caches and temporary
buffers in addition to model weights.</p>

<h2 id="chapter-23">23. Measuring performance and energy</h2>
<p>Performance depends on the workload and the measurement. Latency is
the time for an individual operation; throughput is work completed per
unit time. Clock frequency is cycles per second, not instructions per
second. A simplified CPU time equation is instruction count x average
cycles per instruction / clock frequency. Different architectures and
compilers change instruction count and average cycles.</p>
<p>Memory-bound programs spend substantial time waiting for or
transferring data. Compute-bound programs are primarily limited by
execution capacity. Profilers and hardware counters can help identify
where time is spent. Good benchmarking controls input size, compiler
options, warm-up, system load and power mode, repeats measurements and
reports uncertainty. Synthetic tests are useful but do not necessarily
predict real applications.</p>
<p>Amdahl’s law shows the limit of accelerating only part of a workload:
speedup = 1 / ((1-p) + p/s), where p is the original time fraction
improved and s is its speedup. Increasing clock frequency, core count or
accelerator capability also changes power and heat. Cooling and power
limits may constrain sustained performance. Energy per task can be more
useful than peak speed for battery-powered or large-scale systems.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Measure → Find bottleneck →
Optimize → Measure again" class="flow"><li>Measure</li><li>Find bottleneck</li><li>Optimize</li><li>Measure again</li></ol></figure>
<p><strong>Amdahl’s law:</strong> If 80% of a program becomes four times
faster, overall speedup = 1 / (0.2 + 0.8/4) = 2.5 times, not four times.
Optimizing the remaining part may now offer more benefit.</p>
<p class="sources">Sources: <a aria-label="Reference 1" href="#ref-1">1</a>, <a aria-label="Reference 10" href="#ref-10">10</a>, <a aria-label="Reference 19" href="#ref-19">19</a></p>
<h3 id="latency-throughput-ipc-and-cpu-time-equations">23.2 Latency,
throughput, IPC and CPU-time equations</h3>
<p>Latency measures time for one operation or request, while throughput
measures completed work per unit time. A CPU performance model can
express elapsed processor time as instruction count multiplied by
average cycles per instruction and divided by clock frequency. IPC is
the reciprocal of CPI over a matching measured interval.</p>
<p>These metrics have limited meaning without a workload and measurement
boundary. A higher clock frequency can be offset by more cycles per
instruction or longer memory stalls. A system with high throughput can
still deliver poor individual request latency if queues grow. Benchmark
reports should state configuration, units, input size and whether I/O
time is included.</p>

<h3 id="amdahls-law-and-parallel-scaling">23.3 Amdahl’s law and parallel
scaling</h3>
<p>Parallel execution can accelerate the fraction of a workload that can
run concurrently. Amdahl’s law gives an ideal speedup of 1 / ((1 - p) +
p / N), where p is the parallelizable fraction and N is the number of
equally capable workers. The serial portion limits speedup even if the
parallel portion becomes extremely fast.</p>
<p>Real scaling includes scheduling, synchronization, communication and
shared-resource costs. Some workloads have more useful parallelism as
their problem size increases; others saturate memory bandwidth before
reaching all available cores. Measuring both fixed-size and growing-size
workloads helps distinguish these cases.</p>

<h3 id="profiling-bottlenecks-and-thermal-limits">23.4 Profiling,
bottlenecks and thermal limits</h3>
<p>Profiling observes how a program uses time and resources. Sampling
profilers estimate where execution spends time; instrumentation records
selected events and durations. Hardware performance counters may expose
cache misses, branch events or other architecture-specific behavior.
Each measurement tool introduces limitations and sometimes overhead.</p>
<p>A CPU-bound task is limited primarily by execution resources, while a
memory-bound task spends substantial time waiting for or moving data. An
I/O-bound task depends on external storage or network service. Thermal
and power limits can change operating frequency during long workloads.
Short benchmarks may not represent sustained performance.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Measure baseline → Identify

<p><strong>A fair experiment:</strong> Compare two algorithms on
identical input, hardware, compiler settings and thread counts. Run
repeated trials, report a median and variability, and record whether
caches were warm or cold. Do not infer universal speed from a single
unusually fast trial.</p>

<h2 id="chapter-24">24. Computer security and reliability</h2>
<p>Security protects confidentiality, integrity and availability.
Hardware privilege levels and memory permissions separate application
code from sensitive system resources. Operating-system access controls
restrict files and devices. Cryptographic techniques protect data
against unauthorized disclosure or modification, but their effectiveness
depends on key handling, implementation and correct trust decisions.</p>
<p>A verified boot chain checks authorized code before execution;
measured boot can record component measurements for later evaluation.
Firmware resilience also requires detecting and recovering from
corruption. Sandboxing reduces application privileges, and timely
updates address known defects. Network encryption protects traffic
between endpoints but cannot by itself make an endpoint trustworthy.
Users and administrators still need appropriate authentication and
backups.</p>
<p>Reliability is related but distinct. ECC memory can detect and,
within its design limits, correct certain errors. Storage devices use
error detection and correction, and redundant systems may tolerate
component failures. Checksums detect many forms of accidental corruption
but are not necessarily cryptographic authentication. Defense in depth
combines controls across hardware, firmware, OS, applications and
operations, since no single control covers every failure mode.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Hardware trust → OS isolation → App
permissions → Recovery + backup" class="flow"><li>Hardware trust</li><li>OS isolation</li><li>App
permissions</li><li>Recovery + backup</li></ol></figure>
<p><strong>Least privilege:</strong> A photo viewer should not need
administrator access merely to display a photo. Restricting privileges
reduces the impact of a software defect or compromised application.</p>
<p class="sources">Sources: <a aria-label="Reference 11" href="#ref-11">11</a>, <a aria-label="Reference 15" href="#ref-15">15</a>, <a aria-label="Reference 23" href="#ref-23">23</a>, <a aria-label="Reference 25" href="#ref-25">25</a></p>
<h3 id="memory-protection-permissions-and-least-privilege">24.2 Memory
protection, permissions and least privilege</h3>
<p>Operating systems use hardware protection features and software
policy to restrict access to resources. Page permissions can separate
executable code, writable data and inaccessible regions. Process
isolation prevents ordinary programs from directly reading another
process’s memory unless an authorized interface permits it.</p>
<p>Least privilege means granting only the access necessary for a task.
File permissions, user identities, service accounts and sandbox policies
can reduce the impact of errors. Defense in depth combines independent
protections because a single mechanism can fail. Updates, backups and
careful configuration remain essential even when hardware isolation is
present.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Identity → Permission check →
Allowed resource → Auditable action" class="flow"><li>Identity</li><li>Permission check</li><li>Allowed resource</li><li>Auditable action</li></ol></figure>
<p><strong>A read-only service:</strong> A service that only needs to
read a public document directory should not automatically receive write
access to system configuration or unrelated user files. Limiting those
permissions reduces the possible consequences of a software fault.</p>
<p class="sources">Sources: <a aria-label="Reference 10" href="#ref-10">10</a>, <a aria-label="Reference 11" href="#ref-11">11</a>, <a aria-label="Reference 15" href="#ref-15">15</a></p>
<h3 id="encryption-hashing-and-digital-signatures">24.3 Encryption,
hashing and digital signatures</h3>
<p>Encryption transforms data under a key so authorized parties can
recover it. Authenticated encryption additionally protects integrity
under its security assumptions. A cryptographic hash produces a
fixed-length digest; it is not a reversible encryption function.
Password storage uses specially designed password-hashing methods rather
than a simple fast hash alone.</p>
<p>Digital signatures allow a verifier to check that a message
corresponds to a signing key and has not been altered under the scheme’s
assumptions. Public-key certificates associate keys with identities
through a trust framework. Security depends on key protection,
randomness, correct protocol use and implementation, not just selecting
a famous algorithm name.</p>

<h3 id="reliability-ecc-backups-and-failure-recovery">24.4 Reliability,
ECC, backups and failure recovery</h3>
<p>Digital systems can fail due to hardware defects, transient
disturbances, firmware issues or software errors. Error-detecting codes
add redundant information so certain corruptions can be detected.
Error-correcting codes can also recover from defined error patterns,
with capability depending on the code and system design.</p>
<p>Reliability requires multiple layers: hardware monitoring, filesystem
consistency, service redundancy, backups and tested recovery procedures.
RAID can improve availability against some disk failures but is not a
backup because it may replicate accidental deletion or corruption.
Backups must be independently recoverable and tested against realistic
failures.</p>

<h2 id="chapter-25">25. The future: chiplets, specialized systems and
quantum</h2>
<p>Future computing improvements are not solely about making transistors
smaller. Engineers increasingly optimize communication, packaging and
memory placement. Chiplets can combine dies optimized for different
functions, while advanced packaging brings components closer together.
High-bandwidth memory and near-memory processing address data-movement
bottlenecks. Specialized accelerators trade some generality for
efficiency on particular operations.</p>
<p>Classical computing uses bits and digital logic. Quantum computing
instead manipulates quantum states using qubits and quantum gates, with
measurement producing classical outcomes. Quantum algorithms may offer
advantages for particular problem classes, but qubits are vulnerable to
noise. Error correction encodes logical information across physical
resources and introduces substantial overhead. Quantum hardware is not a
general replacement for ordinary CPUs, memory or operating systems.</p>
<p>Research also explores new device materials, photonic communication,
neuromorphic circuits and more energy-efficient software. These
approaches differ in maturity and suitability. Claims about future
capabilities should distinguish laboratory demonstrations, commercially
available systems and theoretical results. The durable lesson is that
computing progress is a whole-system problem, involving devices,
circuits, architecture, software, algorithms and economics.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Devices → Architecture → Algorithms
→ System efficiency" class="flow"><li>Devices</li><li>Architecture</li><li>Algorithms</li><li>System efficiency</li></ol></figure>
<p><strong>Specialization tradeoff:</strong> A matrix accelerator can be
highly efficient for dense numerical operations yet cannot replace all
the control logic, operating-system tasks and irregular workloads a
general-purpose CPU handles.</p>
<p class="sources">Sources: <a aria-label="Reference 5" href="#ref-5">5</a>, <a aria-label="Reference 6" href="#ref-6">6</a>, <a aria-label="Reference 20" href="#ref-20">20</a>, <a aria-label="Reference 28" href="#ref-28">28</a></p>
<h3 id="chiplets-stacked-memory-and-heterogeneous-integration">25.2
Chiplets, stacked memory and heterogeneous integration</h3>
<p>A chiplet architecture combines multiple dies in one package rather
than placing every subsystem on a single large die. Different dies can
be optimized for different manufacturing processes or functions.
High-density package connections can provide substantial bandwidth,
although communication between dies introduces physical constraints and
design complexity.</p>
<p>Stacked memory places multiple memory dies in a closely connected
structure. High-bandwidth memory interfaces use many parallel
connections to support data-intensive workloads. Packaging must manage
heat, power delivery, signal integrity and testability. The best
partition of functions depends on yield, cost and performance, not
integration alone.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Compute die → Package interconnect
→ I/O die → Memory stack" class="flow"><li>Compute die</li><li>Package interconnect</li><li>I/O die</li><li>Memory stack</li></ol></figure>
<p><strong>A partitioning trade-off:</strong> An arithmetic subsystem
may benefit from a dense leading-edge process, while some I/O circuits
may be suitable for a different process. Combining these dies could
reduce certain costs, but added package complexity and inter-die latency
must be considered.</p>

<h3 id="embedded-edge-and-specialized-computing">25.3 Embedded, edge and
specialized computing</h3>
<p>Embedded systems often interact directly with sensors and actuators
and may require predictable response times. A real-time system is one
whose correctness depends partly on when results arrive. A fast average
response does not guarantee a deadline; designers consider worst-case
behavior and resource contention.</p>
<p>Specialized accelerators implement selected operations using
structures adapted to a workload. Examples include digital signal
processors, video codecs and neural-network engines. Edge computing
performs computation near the source of data, potentially reducing
network latency or data transfer. Trade-offs include local power,
storage, maintenance and hardware capability.</p>

<h3 id="quantum-computing-a-different-computational-model">25.4 Quantum
computing: a different computational model</h3>
<p>Quantum computation uses quantum states rather than ordinary
deterministic bit states as its fundamental model. A qubit can be
described by amplitudes associated with basis states, and multiple
qubits can have entangled states. Quantum gates transform amplitudes;
measurement yields classical outcomes with probabilities determined by
the state and measurement basis.</p>
<p>Quantum algorithms use interference and other quantum properties to
solve certain problems in ways that may offer advantages under specified
assumptions. They do not make all computations faster. Noise, control,
error correction and resource overhead are major engineering challenges.
Classical computers are still required for control, measurement
processing and ordinary computing tasks.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Prepare qubits → Apply gates →
Interference → Measure outcomes" class="flow"><li>Prepare qubits</li><li>Apply gates</li><li>Interference</li><li>Measure outcomes</li></ol></figure>
<p><strong>One ideal qubit:</strong> A qubit prepared in an equal
superposition of the two computational basis states yields either 0 or 1
with probability one-half when measured in that basis. It does not
reveal both answers in a single measurement. Repeated preparations can
estimate outcome probabilities.</p>

<h2 id="chapter-26">26. End-to-end: opening a website on a computer</h2>
<p>A keyboard or touchscreen reports input to a controller, and device
software turns it into an event. The browser’s event loop processes that
event and interprets the requested URL. The operating system provides
sockets, memory mappings and scheduling; network resolution and
connection setup may happen or be reused from previous activity.</p>
<p>A network interface moves data through device buffers. The kernel and
browser process protocols and authenticate the connection when required.
Received bytes enter memory, perhaps passing through several cache
levels as CPU cores execute parsing, decoding and script instructions.
The browser allocates objects and constructs internal representations of
the document and styles. Some assets may be read from persistent caches
rather than downloaded.</p>
<p>The rendering engine computes sizes and positions, creates drawing
commands and combines layers. GPU work may be scheduled through a
graphics driver. The display engine presents the completed image, and
the user sees the webpage. Beneath this sequence, billions of
microscopic switching events implement logical operations, state
transitions and data transfers. Above it, applications and standards
provide interfaces that make the entire process programmable.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Input event → Network + browser →
CPU / GPU work → Visible webpage" class="flow"><li>Input event</li><li>Network + browser</li><li>CPU / GPU work</li><li>Visible webpage</li></ol></figure>
<p><strong>The central insight:</strong> The computer never has to
understand a webpage the way a human does. It follows precisely defined
representations and operations, whose combined behavior produces the
experience we recognize.</p>
<p class="sources">Sources: <a aria-label="Reference 9" href="#ref-9">9</a>, <a aria-label="Reference 11" href="#ref-11">11</a>, <a aria-label="Reference 13" href="#ref-13">13</a>, <a aria-label="Reference 22" href="#ref-22">22</a>, <a aria-label="Reference 23" href="#ref-23">23</a>, <a aria-label="Reference 24" href="#ref-24">24</a>, <a aria-label="Reference 25" href="#ref-25">25</a>, <a aria-label="Reference 26" href="#ref-26">26</a>, <a aria-label="Reference 27" href="#ref-27">27</a></p>
<h3 id="case-study-launching-an-application">26.2 Case study: launching
an application</h3>
<p>When a user selects an application, the desktop environment requests
that the OS start the appropriate executable or invoke an existing
process. For a new process, the kernel establishes an address space and
initial thread. The executable loader maps code and data, and a dynamic
loader may resolve required libraries.</p>
<p>The application’s runtime initializes its environment and then enters
its main logic. On-demand page faults may bring code or data into memory
from storage. The scheduler gives the thread CPU time, while the
application creates interface surfaces and registers event handlers. A
compositor eventually makes its window visible.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Launch request → Map executable →
Initialize runtime → Show window" class="flow"><li>Launch request</li><li>Map executable</li><li>Initialize runtime</li><li>Show window</li></ol></figure>
<p><strong>Cold versus warm launch:</strong> A first launch after
startup may need to fetch more code and data from storage. A later
launch can benefit from file-system caches, even if the application
itself has been closed. That difference illustrates why benchmark cache
state matters.</p>

<h3 id="case-study-reading-and-saving-a-file">26.3 Case study: reading
and saving a file</h3>
<p>To open a file, a program usually requests an OS-managed handle. The
kernel resolves the path, checks permissions and accesses file-system
metadata. Subsequent reads may be served from cached pages; misses lead
to block-device requests and eventual completion notifications. The
program interprets returned bytes according to the file format.</p>
<p>Saving reverses part of the data flow but also changes metadata and
requires attention to consistency. An application may transform its
in-memory state into a serialized representation, issue writes and
request durability when necessary. Storage hardware maintains
logical-to-physical mappings and completes requests according to its
interface guarantees.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Open and validate → Read or modify
bytes → Write / synchronize → Close resource" class="flow"><li>Open and validate</li><li>Read or modify
bytes</li><li>Write / synchronize</li><li>Close resource</li></ol></figure>
<p><strong>Why formats matter:</strong> A file containing the text 123
stores characters, whereas a binary file may store the number 123 in a
fixed-width integer field. Both can be correct, but a reader needs the
format specification to interpret the bytes correctly.</p>

<h3 id="case-study-typing-a-letter-and-seeing-it-appear">26.4 Case
study: typing a letter and seeing it appear</h3>
<p>A keyboard controller detects changes in key state and sends input
reports through its interface. The operating system’s input subsystem
translates reports into events and routes them according to focus and
policy. A keyboard layout and input method determine how key events
become text. Pressing a key is not necessarily equivalent to producing a
single character.</p>
<p>The application updates its internal text state and requests a visual
update. Text shaping selects and positions glyphs from fonts; layout
determines placement; painting and compositing create or update a
visible surface. The display controller presents the resulting pixels.
The whole sequence crosses hardware, drivers, OS services and
application code.</p>

<p><strong>The letter A:</strong> With a typical English layout,
pressing a letter key while Shift is active can produce uppercase A. A
different layout or input method may interpret the same key differently.
The physical key identifier, Unicode character and rendered glyph are
separate representations.</p>

<h2 id="chapter-27">27. Practical study and verification exercises</h2>
<p>Start at digital logic. Build a truth table for a half adder and a
full adder using a logic simulator or a short program. Check all eight
full-adder input combinations. Then implement a fixed-width binary adder
in software and inspect both the sum and carry-out. Explain the
difference between signed and unsigned overflow using four-bit
operands.</p>
<p>Move to architecture. Use a RISC-V emulator or an educational
simulator to step through ADD, load, store and branch instructions.
Record PC and register changes. Compile a simple function at two
optimization levels and compare assembly; do not assume every source
variable becomes a physical register. For Python, use the standard dis
module to inspect interpreter bytecode and contrast it with native
machine instructions.</p>
<p>Finally explore systems. Use a task manager or system monitor to
observe CPU, memory, storage and network activity while opening an
application. Compare sequential and random array traversal using
repeatable local benchmarks, keeping dataset size and runtime conditions
explicit. Record actual observations and distinguish them from
expectations. Use browser developer tools to study a page’s network
requests and rendering timing. These experiments link the explanations
in this guide to measurable behavior without needing to open or modify
physical hardware.</p>
<figure class="diagram"><figcaption>Concept diagram</figcaption><ol aria-label="Simulate logic → Inspect assembly →
Observe OS → Measure workload" class="flow"><li>Simulate logic</li><li>Inspect assembly</li><li>Observe OS</li><li>Measure workload</li></ol></figure>
<p><strong>Self-test:</strong> Why is GHz not instructions per second?
Why can a page fault occur without disk access? Why does a file write
not always imply durability? Why can GPU acceleration lose to a CPU for
a small task? Explain each using the relevant chapter.</p>

of each carry to verify the intermediate states. The test cases should
include zero, a chain of carries and a result that exceeds the chosen
width. This can be done entirely on paper or in software.</p>

version, architecture and flags, since output is not universal.</p>

Python program, the documented dis module can show the bytecode of a

instructions. The runtime implements its execution semantics using

misses. However, language overhead, data size, compiler optimization and
cache capacity can obscure the effect. Use results to form a hypothesis
rather than treating one run as proof of a universal hardware

<li><strong>Page:</strong> Fixed-size unit in a particular virtual
memory mapping scheme.</li>
<li><strong>Pipeline:</strong> Overlapped processing of work through
multiple stages.</li>
<li><strong>RAM:</strong> Random-access memory; often used to refer to
volatile main memory.</li>
<li><strong>Register:</strong> Small architectural or internal processor
storage location.</li>
<li><strong>RTL:</strong> Register-transfer level description of a
digital circuit.</li>
<li><strong>SIMD / SIMT:</strong> Data-parallel instruction / thread
execution models.</li>
<li><strong>SoC:</strong> System on a chip; integrates multiple system
functions.</li>
<li><strong>SRAM:</strong> Static random-access memory; retains state
while powered.</li>
<li><strong>SSD:</strong> Solid-state drive; typically stores data in
nonvolatile flash.</li>
<li><strong>System call:</strong> Controlled request from software to
the OS kernel.</li>
<li><strong>TLB:</strong> Translation lookaside buffer; caches address
translations.</li>
<li><strong>TLS:</strong> Transport Layer Security; cryptographically
protected communication.</li>
<li><strong>UEFI:</strong> Unified Extensible Firmware Interface.</li>
<li><strong>Virtual memory:</strong> Address-space abstraction with
translation and protection.</li>
<li><strong>Wafer:</strong> Semiconductor substrate on which multiple
dies are fabricated.</li>
<li><strong>Working set:</strong> Data or pages actively needed during a
given interval.</li>
</ul>
